### Phase 57: Semantic Store Foundation + Pipeline DAG Library
**Goal**: A semantic fact store opens at daemon start, configuration flows through the existing 4-layer precedence, and a stdlib pipeline-DAG library is available for the new graphs to consume — without touching the existing imperative bootstrap.
**Depends on**: Nothing (first v1.10 phase; foundation)
**Requirements**: STORE-01, STORE-02, STORE-03, STORE-04, STORE-05, STORE-06, DAG-01, DAG-02, DAG-03, DAG-04
**Success Criteria** (what must be TRUE):
  1. With `semantic_index.enabled=true`, a fresh daemon start opens (or quarantines + rebuilds) `<workspace>/.helix/semantic.duckdb` and `get_health` reports the store as ready.
  2. With `semantic_index.enabled=false` (or implicit-false because CGO=0 has no tree-sitter), every semantic-dependent tool returns `Kind: Unsupported` with remediation text and the rest of Helix continues to serve requests.
  3. A `go vet`-runnable lint fails the build if any package outside `internal/semantic/store/` imports `duckdb-go`.
  4. The semantic indexer, live-update, and eval pipelines each declare typed phase DAGs that the `internal/phasegraph/` library validates (cycle / missing-dep / duplicate-id) before execution; daemon bootstrap remains imperative and carries a `// TODO(v1.11): migrate to phasegraph.RunPhaseGraph` marker.
  5. Every new `semantic_index.*` config key resolves under the documented 4-layer precedence (CLI > project > user > profile) and is covered by the existing config-coverage test.

### Phase 60: Live Update Pipeline
**Goal**: Source changes — from editor saves, file moves, and Helix's own edit tools — flow into the live overlay deterministically, survive editor atomic-rename save patterns, and never silently miss events.
**Depends on**: Phase 57, Phase 59
**Requirements**: LIVE-01, LIVE-02, LIVE-03, LIVE-04, LIVE-05, LIVE-06, LIVE-07
**Success Criteria** (what must be TRUE):
  1. The directory-level fsnotify watcher catches every save under Vim, JetBrains (`___jb_tmp___` + rename), and VS Code atomic-rename save patterns — verified by an editor-fixture test.
  2. The required (not best-effort) periodic content-hash scrub catches missed events; status surfaces via `get_semantic_graph_status`.
  3. Linux `inotify` `ENOSPC` falls back to manifest-poll mode per workspace with a user-visible warning; semantic queries still answer with stale-allowed reads.
  4. After every successful `replace_symbol_body`, `insert_before/after_symbol`, `rename_symbol`, `safe_delete_symbol`, `replace_in_file`, and `fuzzy_edit`, a `ChangeHelixEdit` event lands in the live queue via `postEditHook` (kernel does not import semantic).
  5. Overlay writes carry a monotonic `overlay_epoch`; bulk-change events above `live_updates.bulk_change_threshold` (default 200) collapse to a single `bulk_update` event.

### Phase 62: Graph Engine, Ranking & Type Resolution
**Goal**: A deterministic weighted PageRank single projection ships with `graph_version`-stamped responses, bounded incremental repair, weak-component clustering, and tiered type-resolution that bounds fixpoint depth and never claims false certainty.
**Depends on**: Phase 60, Phase 61
**Requirements**: GRAPH-01, GRAPH-02, GRAPH-03, GRAPH-04, GRAPH-05, GRAPH-06, TYPES-01, TYPES-02, TYPES-03, TYPES-04
**Success Criteria** (what must be TRUE):
  1. Same input across runs produces byte-identical PageRank scores (stable-key NodeID tiebreak); personalized PageRank with seed weighting returns a ranked node list under `pagerank.epsilon=1e-6`.
  2. Every ranked envelope carries `graph_version`, `enrichment_level`, and `score_status` (`exact | approximate | stale | missing`); incremental local repair runs only inside the `max_local_pagerank_nodes` frontier (default 5000).
  3. A deterministic weak-component pass identifies clusters; cluster MCP tools are deferred to v1.10.x but the algorithm is shipped and tested.
  4. Type-resolution emits `RESOLVES_TO`, `CALLS`, and `USES_TYPE` edges with confidence per the SPEC §38.2 ladder; access chains up to `max_chain_depth=8` resolve under a fixpoint loop bounded by `max_fixpoint_iterations=8`.
  5. Comment-derived edges (JSDoc / TSDoc / PHPDoc / YARD / Python type comments) never exceed confidence 0.60 unless independently confirmed by LSP; non-converged chains are emitted with `unresolved` markers, never `validated`.

### Phase 63: Compaction & Retention
**Goal**: The live overlay folds into committed snapshots without losing rows under concurrent writes or daemon crashes, while bounded on-disk growth keeps long-lived repos performant.
**Depends on**: Phase 60, Phase 62
**Requirements**: COMPACT-01, COMPACT-02, COMPACT-03, COMPACT-04, COMPACT-05
**Success Criteria** (what must be TRUE):
  1. Compaction runs after `compact_after_idle_ms` (default 5000) when no edit/overlay/LSP transaction is active; a property test ("interleave overlay writes with compaction") passes — no overlay rows committed during compaction are dropped by `ClearOverlay`.
  2. A kill-mid-compact integration test confirms a single transaction OR a `compaction_journal` leaves overlay+snapshot consistent on restart.
  3. A `CHECKPOINT` runs at compaction commit; a config-gated weekly `VACUUM` keeps the long-repo bench fixture's `.duckdb` file growth bounded across 1000 simulated commits.
  4. Snapshot retention keeps the last `snapshot_retention=5` snapshots; older snapshots are deleted in a single transaction.

### Phase 66: Agent Guardrails (G-001..G-005, warn-default)
**Goal**: Five warn-default guardrails block agent footguns (rename-by-grep, delete-without-references, public-API edit without blast-radius, large fuzzy edit without prior context, security-sensitive change without diagnostics) using server-side safety receipts that survive client context compaction.
**Depends on**: Phase 62, Phase 65
**Requirements**: GUARD-01, GUARD-02, GUARD-03, GUARD-04, GUARD-05, GUARD-06, GUARD-07
**Success Criteria** (what must be TRUE):
  1. `GuardrailMiddleware` is installed at daemon step 14b.5 and the LIFO execution order is `LazyInit → Guardrail → Suggestion → ProfileFilter → Telemetry → handler` (LazyInit-last invariant preserved, regression-asserted).
  2. G-001..G-005 enforce at warn-default; an integration test where the agent's context is artificially truncated proves a destructive tool refuses without a server-side receipt match (ID-only forwarding survives compaction).
  3. Receipts auto-invalidate when `graph_version` advances past the receipt's snapshot; `helix_receipt_expired_total` and `guardrail_blocked` / `guardrail_warned` outcome classes show in RED metrics.
  4. `GUARDRAILS.md` and `DoD.md` are committed and explain rule semantics + completion criteria for rename / delete / public-API-change task classes.
  5. Enforcement levels (`off | warn | require_force | enforce`) are configurable per profile; default is `warn` for `read`/`edit` profiles and `require_force` for `review` profile on high-risk pre-checks.

### Phase 67: Evaluation Harness
**Goal**: An out-of-process eval harness proves Helix improves agent success / cost / safety by running the same tasks under `baseline / native / semantic / semantic_guarded` and emitting per-task evidence — without leaking proprietary code into commercial LLM training pipelines.
**Depends on**: Phase 66
**Requirements**: EVAL-01, EVAL-02, EVAL-03, EVAL-04, EVAL-05, EVAL-06, EVAL-07
**Success Criteria** (what must be TRUE):
  1. `make eval` runs all four modes against the same task corpus; each mode runs in an out-of-process Helix daemon subprocess with isolated config dir; baseline mode uses `--profile=baseline` (Helix tools stripped); the agent connects via stdio forwarder.
  2. `make eval-quick` runs a small fixture suite in-process for fast local CI without subprocess overhead.
  3. Reports include `eval_report.json`, `eval_report.md` (mode comparison, success/cost/latency, tool-call distribution, guardrail compliance, failure examples), `cost_summary.json`, `tool_behavior.json`, `safety_compliance.json`, plus per-task traces and patches.
  4. Tool-behavior scoring records whether agents used the right tool for rename/delete/public-API tasks; eval corpus is synthetic-only by default with the OSS Helix repo as a permissible secondary source; provider data-retention TOS is verified at planning time and recorded in `EVAL.md`; commercial-LLM API calls are configured for retention-zero where supported.
  5. Cross-model judging is informational and never blocks a CI merge.
