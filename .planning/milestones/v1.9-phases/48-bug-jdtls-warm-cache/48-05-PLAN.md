    ```yaml
        steps:
          - uses: actions/checkout@v4

          - name: Set up Go

              java-version: '17'

          - name: Install jdtls
            run: |
              pipx install "jdtls==${JDTLS_VERSION}"
              jdtls --help > /dev/null 2>&1 || true
              echo "$HOME/.local/bin" >> "$GITHUB_PATH"

          - name: Cache warm jdtls workspace
            uses: actions/cache@v3
            with:
              path: ~/.cache/serena-test/jdtls
              key: jdtls-warm-${{ runner.os }}-${{ hashFiles('testdata/fixtures/java/**') }}-jdtls-${{ env.JDTLS_VERSION }}
              restore-keys: |
                jdtls-warm-${{ runner.os }}-

          - name: go vet
            run: go vet ./...

          - name: go test
            run: go test ./... -count=1
    ```

    ```markdown
    ### Java integration tests (warm jdtls cache)

    Serena's Java integration suite (`test/integration/java_test.go`) runs as part of
    the default `go test ./...`. First-time runs are slow because jdtls must index the
    Java fixture; subsequent runs reuse a persistent workspace under the user cache
    directory, cutting wall-clock dramatically.

    **Cache location:**

    - Linux: `$XDG_CACHE_HOME/serena-test/jdtls/<fixture-hash>-<jdtls-hash>/` (default `~/.cache/...`).
    - macOS: `~/Library/Caches/serena-test/jdtls/...`.
    - Windows: `%LocalAppData%\serena-test\jdtls\...`.

    The cache key is derived from the Java fixture contents (`testdata/fixtures/java/**`)
    and the resolved `jdtls` binary identity. Changing either produces a new directory;
    old ones coexist until manually cleaned.

    **Commands:**

    - `go test ./test/integration/ -run 'TestSymbols_JavaFixture|TestEdit_JavaFixture' -count=1` — run the Java suite once. Skips cleanly if `jdtls` is not on PATH.
    - `make bench-jdtls-warm` — wipe the cache, run the Java suite cold, then run it warm; prints both wall-clocks.
    - `make clean-jdtls-cache` — remove `$XDG_CACHE_HOME/serena-test/jdtls/` (POSIX only; on Windows delete the folder manually).

    **Test-only environment variable:**

    `SERENA_TEST_JDTLS_DATA_DIR` — when set to a non-empty absolute path, Serena's
    jdtls adapter uses that path as the `-data` argument instead of the default
    `workDir/.jdtls-data`. This is the seam the Java integration tests use to inject
    the warm cache directory. **Do not set this variable in production.**

    **Known limitations:**

    - Running two `go test ./...` invocations concurrently against the same fixture
      will race on the warm `-data` directory — jdtls requires an exclusive workspace
      lock. Mitigation: avoid concurrent integration-test runs on the same machine,
      or run `make clean-jdtls-cache` between them. A file-system advisory lock is
      tracked as a follow-up (see RESEARCH.md Pitfall 4; deferred beyond Phase 48).
    - CI reuses the same cache via `actions/cache@v3` in `.github/workflows/go-test.yml`;
      cache misses (new fixture content or new jdtls version) fall back to cold start.
    ```

    **Step C — verify placement:** the new subsection must NOT break existing table-of-contents or link anchors. Grep for any `#java-integration` anchor first; if one exists elsewhere, adjust the heading slug accordingly.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → external `pipx install jdtls` | Downloads and executes arbitrary code from PyPI per pinned version |
| CI cache → fresh job restore | `actions/cache@v3` persists jdtls workspace across workflow runs |
| USAGE.md readers → exposed env-var contract | Documentation describes a runtime knob (SERENA_TEST_JDTLS_DATA_DIR) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-48-05-01 | Tampering | Malicious or compromised jdtls PyPI package | mitigate | Pin version via `JDTLS_VERSION: "1.57.0"` env — cannot silently upgrade. Long-term: mirror or checksum-verify (deferred to Phase 50 supply-chain hardening). |
| T-48-05-02 | Tampering | Cached warm workspace contains attacker-controlled payload across runs | mitigate | Cache scope is `~/.cache/serena-test/jdtls` — restored into fresh runner per-job; cannot escape to host. Key includes `hashFiles('testdata/fixtures/java/**')`, so fixture edits in a PR invalidate stale cache. Per-PR runners are ephemeral. |
| T-48-05-03 | Information Disclosure | Workflow logs leak file paths, Go module versions, jdtls version | accept | These are already public information (open-source repo). No secrets involved. |
| T-48-05-04 | Denial of Service | Attacker crafts a PR with a huge `testdata/fixtures/java/` tree to blow the cache budget | accept | Repo is source-controlled; reviewers see the diff. GitHub's cache limit (10 GB per repo) bounds worst case. Not a new surface. |
| T-48-05-05 | Elevation of Privilege | Workflow permissions too broad | mitigate | `permissions: contents: read` explicitly set at job level — no write scope. Matches `bench.yml` convention. No secrets referenced. |
| T-48-05-06 | Repudiation | No provenance/attestation on workflow runs | accept | Standard CI logs suffice for v1.9; full SLSA attestation is out of scope (Phase 51 packaging concern). |
| T-48-05-07 | Spoofing | USAGE.md readers misinterpret `SERENA_TEST_JDTLS_DATA_DIR` as a production feature | mitigate | Section explicitly labels it "Test-only environment variable" and states "Do not set this variable in production." Grep acceptance criterion enforces this sentence. |

**ASVS L1 relevance:**
- V14.1 (build pipeline) — workflow runs on a pinned Ubuntu image with pinned Go and Java versions.
- V14.2 (dependency management) — jdtls version pinned via env; actions pinned to `@v3`/`@v4`/`@v5` (consistent with repo-wide pattern).
- V1.1 (secure SDLC) — PR trigger with `contents: read` only; no write-scope escalation.
</threat_model>
