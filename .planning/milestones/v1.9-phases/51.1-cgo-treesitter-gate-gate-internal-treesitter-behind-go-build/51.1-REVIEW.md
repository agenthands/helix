## Warnings

### WR-01: Windows daemon detach is a silent regression, not just a placeholder concession

**File:** `internal/forwarder/dial_windows.go:11`
**Issue:** `detachFromProcessGroup` is a no-op on Windows. The comment justifies this with "goreleaser only ships Windows binaries as placeholder archives (DEF-51-02)" — but this conflates two things. Once DEF-51-02 closes (which is the entire point of phase 51.1's follow-up work), Windows binaries become real artifacts and the daemon will inherit the forwarder's console group: a Ctrl-C in the calling shell will kill the daemon along with the forwarder, defeating "Detach daemon from forwarder process group" (the stated intent at `dial.go:90`). Because nothing in the code or tests reminds future-you to revisit this, the regression will ship the day Windows support lands.
**Fix:** Either (a) implement detach now using `syscall.SysProcAttr{CreationFlags: windows.CREATE_NEW_PROCESS_GROUP | windows.DETACHED_PROCESS}` (golang.org/x/sys/windows), or (b) at minimum file a tracked TODO referencing a specific issue/phase ID and add a `t.Skip` in the Windows test path so it cannot be silently forgotten:
```go
//go:build windows

package forwarder

import (
    "os/exec"
    "syscall"
    "golang.org/x/sys/windows"
)

func detachFromProcessGroup(cmd *exec.Cmd) {
    cmd.SysProcAttr = &syscall.SysProcAttr{
        CreationFlags: windows.CREATE_NEW_PROCESS_GROUP | windows.DETACHED_PROCESS,
    }
}
```

### WR-02: `NewTagExtractor` !cgo stub returns `(nil, err)`; callers that ignore err will nil-deref

**File:** `internal/repomap/extractor_nocgo.go:16`
**Issue:** Under !cgo, `NewTagExtractor` returns `(nil, error)`. The current caller in `internal/skill/repomap/skill.go:128` checks the error correctly. But the stub deliberately keeps the `Extract`/`Close` methods on `*TagExtractor` — and a nil receiver passed to `Extract` would not nil-panic (it dereferences no field), yet a nil receiver passed to `Close` is also safe but a future refactor that adds field access will silently regress. More importantly, this is asymmetric with sibling stubs: `NewBodyExtractor` and `NewElisionRenderer` return non-nil empty structs, while `NewTagExtractor` returns nil. The asymmetry is a foot-gun for future callers who copy the BodyExtractor pattern.
**Fix:** Either return a non-nil empty `&TagExtractor{}` with a nil error to match sibling stubs, or document the asymmetry inline. Note: the daemon refusal hook makes this defensive in practice, but the skill explicitly tolerates extractor-creation failure and continues in degraded mode (`s.logger.Warn(...)`), so this stub IS reachable on paper if the refusal hook is ever bypassed (e.g., a future test harness that constructs the skill directly). Recommended:
```go
func NewTagExtractor(_ *treesitter.GrammarRegistry) (*TagExtractor, error) {
    return &TagExtractor{}, nil // matches BodyExtractor/ElisionRenderer pattern; methods return errors
}
```
…or, alternatively, make `NewBodyExtractor`/`NewElisionRenderer` also return `(nil, err)` so all three are uniform. Pick one, document the choice.

### WR-03: `BodyExtractor` cgo and !cgo signatures are not compile-asserted to match

**File:** `internal/kernel/edit/treesitter_nocgo.go:26`
**Issue:** The `ExtractBody` method signature in `treesitter_nocgo.go` is hand-copied from `treesitter.go:219`. If a future change to the cgo signature (e.g., adds a `context.Context` parameter, returns `(int64, int64, error)` instead of `(uint, uint, error)`) is not mirrored here, `CGO_ENABLED=0 go build` breaks at the call site rather than the definition — but the breakage will only surface in CI's nocgo job, not in local CGO=1 development. Same risk for `SupportsLanguage`, `RenderFile`, `ElideSingle`, `Extract`, `Close`, and `GrammarRegistry`'s methods.
**Fix:** Add a compile-time signature assertion in a shared (non-build-tagged) test helper file, e.g. `internal/kernel/edit/sig_assert.go`:
```go
package edit

// Compile-time assertion that BodyExtractor exposes the expected method set
// in BOTH cgo and !cgo builds. Update when ExtractBody's signature changes.
var _ interface {
    SupportsLanguage(string) bool
    ExtractBody([]byte, string, string, gen.Range) (uint, uint, error)
} = (*BodyExtractor)(nil)
```
Repeat for `*TagExtractor`, `*ElisionRenderer`, `*GrammarRegistry`. This catches drift at compile time in both build modes via local `go vet` without needing CI for the signal.

## Info

### IN-01: Refusal-hook error message mentions `CONTRIBUTING.md > Releasing` but operator may not have repo access

**File:** `internal/daemon/daemon.go:201-203`
**Issue:** End users running a downloaded CGO=0 binary won't have `CONTRIBUTING.md` handy — they have a binary and an error message. Pointing them at a docs path that lives only in the repo is mildly user-hostile.
**Fix:** Reference the public docs URL or the GitHub Releases page instead, e.g. "see https://github.com/.../releases for CGO=1 builds".

### IN-02: `registry_nocgo.go` doc comment says "Package treesitter — !cgo stub" but is the canonical package doc under !cgo

**File:** `internal/treesitter/registry_nocgo.go:3-7`
**Issue:** Under CGO=0 builds, godoc tools will pick up this comment as THE package documentation (since `registry_cgo.go`'s package comment is excluded). The phrasing "!cgo stub" is fine for maintainers but reads strangely as the primary package description in godoc. Minor.
**Fix:** Lead with what the package does, then note the build-tag context, e.g. "Package treesitter provides a shared grammar registry for tree-sitter languages. Under CGO_ENABLED=0 this is a stub package..."
