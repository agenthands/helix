## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repo source → binary contents | Every `//go:embed` directive determines what ships inside the binary; an unaudited gap (a file read from disk that should have been embedded) creates a runtime dependency on the install layout that breaks the "single self-contained binary" promise. |
| Binary install dir → external download paths | The three-tier LS installer is the documented external-download surface (D-15); any new disk read NOT going through that installer is a leak of the policy boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-05-01 | Tampering | A future contributor adds a disk-read for an asset that should have been embedded, weakening the "single binary" promise without anyone noticing | mitigate | The Future-Audit Trigger section in `EMBED-AUDIT.md` documents the obligation explicitly. CHANGELOG / CONTRIBUTING entries (Plan 06's responsibility) cross-link to this manifest so PR reviewers consult it. |
| T-52-05-02 | Information Disclosure | The audit accidentally classifies a file containing secrets as "embedded" — secrets ship inside the binary | mitigate | The classification step requires reading each candidate file's content; the planner reads each `//go:embed`'d file before adding it to the Embedded table. The minisign.pub case (only public-key bytes) is the canonical safe example; any new embed of a `.key`/`.pem`/`token` file would surface in the audit and trigger a manual review. |
| T-52-05-03 | Denial of Service | The audit silently misses a category (e.g., `embed.FS` walks vs. `//go:embed` single-file) and undercounts | mitigate | The Audit Method section documents three independent grep commands (`//go:embed`, `os.ReadFile`/`os.Open`, `filepath.Join`); they overlap deliberately so a finding caught only by `os.ReadFile` (an embed.FS Walk consumer) still surfaces somewhere. |
