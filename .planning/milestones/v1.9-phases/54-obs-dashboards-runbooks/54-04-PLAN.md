  Intro: explain that LS workers can die for many reasons (segfault, OOM, malformed jdtls workspace) and that the worker pool detects exit, books an EvictCrash eviction, and starts a new worker subject to the restart budget; if the budget is exhausted the circuit opens.

  Symptoms:
    - helix_lspool_evictions_total{reason="crash"} rate rises.
    - helix_lspool_restarts_total rate rises (if budget not yet exhausted).
    - helix_lspool_workers gauge dips for the affected language.
    - Daemon logs include "lspool worker exited unexpectedly".

  Triage: use the three queries from the interfaces block VERBATIM.

  Likely Causes:
    - LS binary OOM (confirmed by checking `dmesg` on Linux or Console.app on macOS).
    - Repository-specific LS bug (jdtls + bad workspace, rust-analyzer + crate dep mismatch) - confirmed by reproducing on another repo.
    - Helix daemon panic-recovered handler (recovered panics are logged at ERROR with stack).

  Remediation:
    1. (operator) Inspect daemon logs around the crash for the LS exit code and signal.
    2. (operator) If repository-specific: try opening the repo with the LS standalone (e.g., `gopls` directly).
    3. (engineer) If a Helix-side panic is in the recovery log: file an issue with the recovered stack trace.

**docs/runbooks/memory-pressure-eviction.md** (severity: warning, metric: helix_lspool_evictions_total{reason="pressure"}, since_phase: 11)

  Intro: explain that on Linux Helix reads /proc/pressure/memory (PSI) and on macOS it polls vm_stat to detect host memory pressure; under pressure, the worker pool evicts idle LS workers (EvictPressure) before the OOM killer fires.

  Symptoms:
    - helix_lspool_evictions_total{reason="pressure"} rate rises.
    - System-level memory pressure visible to other processes.
    - helix_lspool_workers dips even though no LS crashed.

  Triage: use the two queries from the interfaces block VERBATIM.

  Likely Causes:
    - Other processes (Claude Code, IDE, build) are competing for memory - confirm via ps or Activity Monitor.
    - Helix LS workers are individually large (jdtls warm cache) - confirm via per-worker RSS.
    - Host is undersized for the LS mix - confirm by raising memory and re-observing.

  Remediation:
    1. **(operator) Linux:** `cat /proc/pressure/memory` - interpret avg10 column (values >10 indicate sustained pressure).
    2. **(operator) macOS:** `vm_stat 5` - watch the "Pages free" and "Pages inactive" columns.
    3. (operator) Free memory by closing other tools, or relaunch the daemon with a higher memory ceiling.
    4. (engineer) If the eviction rate stays high under no apparent pressure, verify pressure_linux.go / pressure_darwin.go thresholds.

  Code references: pressure_linux.go (PSI read around line 22), pressure_darwin.go (vm_stat around line 24), pool.go (evictWorkerLocked(EvictPressure) around lines 403/432/452), pressure.go (PressureLevel enum around lines 9-15), metrics.go (EvictPressure constant around line 38). Use SMTC-verified line numbers.
