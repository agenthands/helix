<objective>
Fix the cross-process daemon-spawn race in `ConnectOrStartDaemon` so N parallel cold
`helix` callers spawn exactly one daemon. Today `internal/forwarder/dial.go:26-39` has an
unlocked window: try-connect → startDaemon → waitForDaemon, with NO mutual exclusion, so
every cold caller forks its own daemon (N-1 then fail `net.Listen` and exit — wasteful
forks + connect storm). Add a per-socket `gofrs/flock` guard around the spawn window with
double-checked `tryConnect` after lock acquisition (TOCTOU fix, RESEARCH Pitfall 1). Pin
the in-process lock/double-check ALGORITHM with a deterministic `testing/synctest` test
(real-PID assertion is deferred to the E2E oracle in plan 90-04, RESEARCH Pitfall 4).

Purpose: CLI-03 — race-free auto-start is the foundation every later `helix <verb>`
invocation rides on; without it parallel agent calls fork a daemon storm.
Output: flock dependency added + provenance-verified; `dial.go` lock guard; `dial_lock.go`
helper with a spawn-counter seam; synctest race-algorithm test.
</objective>

      signal, takes the reuse path (its tryConnect succeeds) and does NOT increment the spawn counter.
    - Test 3 (double-check TOCTOU): a caller whose pre-lock tryConnect failed but whose
      post-lock tryConnect succeeds (peer finished between probe and lock) does NOT spawn.
    - Test 4 (per-socket key): two callers on DISTINCT socket paths each spawn once

  <action>
    Introduce a spawn seam so the lock ALGORITHM is testable without real exec: in
    `dial_lock.go` define a package-level function variable (e.g. `spawnDaemon = startDaemon`)
    that the race test overrides with a counting fake, and a small helper
    `lockfilePath(socketPath string) string` returning `socketPath + ".lock"` (a regular
    file, never bind()ed, so it is not AF_UNIX-length-limited — RESEARCH Pitfall 2). The

    a per-socket `flock.New(lockfilePath(socketPath))`: `TryLock()`; if NOT acquired, the
    peer is spawning — `Lock()` to block until the peer releases (its socket is up),
    `defer Unlock()`, then `tryConnect` and return on success (lock-loser reuse). If
    acquired, `defer Unlock()`. After acquiring the lock by EITHER path, ALWAYS re-run
    `tryConnect` (double-checked locking, RESEARCH Pitfall 1 — a peer may have finished

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| go module supply chain → build | a newly `go get`'d package executes in the dial path |
| CLI process → shared /tmp lockfile/socket | the per-socket lockfile + unix socket live under a shared-tmp per-uid dir |
| concurrent CLI processes → daemon spawn | N untrusted-timing callers race to fork a daemon |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-90-SC | Tampering | `go get github.com/gofrs/flock@v0.13.0` | mitigate | Task 1 blocking `checkpoint:human-verify` confirms maintainer/repo/version on pkg.go.dev before install; go.sum pins hashes. Never auto-approvable. |
| T-90-01 | Tampering | per-socket lockfile path in shared /tmp (symlink attack) | mitigate | Lockfile derives from the existing per-uid 0700 socket dir (`socket.go createSocketDir`); flock opens a regular file (never bind), inheriting 0700 perms — no new path code. |
| T-90-02 | DoS | duplicate-daemon spawn under N parallel callers (connect storm) | mitigate | The flock startup lock (Task 2) prevents redundant spawns; daemon `net.Listen("unix")` bind (daemon.go:1318) is the defense-in-depth backstop. |
| T-90-03 | DoS | stale lockfile from a crashed holder blocking forever | accept | OS advisory flock auto-releases when the holding process dies (kernel-managed); no manual stale-lock GC needed — this is precisely why flock beats a pidfile. |
