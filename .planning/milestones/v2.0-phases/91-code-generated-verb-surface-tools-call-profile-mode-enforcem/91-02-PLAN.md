<objective>
Add a `tools/call` profile/mode enforcement middleware — the load-bearing
security fix for this phase. Today `ProfileFilterMiddleware` filters ONLY
`tools/list`; there is no `tools/call` rejection path, so the moment Plan 91-01
makes every verb always-invocable, a read-mode or ci-bot agent could call a
destructive edit verb. The new middleware is a near-verbatim clone of the
verified `GuardrailMiddleware`: early-out on non-`tools/call`, read the session's
already-resolved `AllowedTools` snapshot, and refuse a tool outside that set with
a typed `serr.PermissionDenied` error so `errors.Is` round-trips to the CLI.

Purpose: SEC-01 — close the privilege-escalation regression the always-visible
verbs would otherwise open. Authz MUST be server-side (the daemon session is
authoritative; the CLI never sees profile/mode); a CLI-only check is bypassable.
Output: `internal/mcp/profile_enforce.go` + test, and the daemon install wiring
placed AFTER Guardrail and BEFORE LazyInit (preserving the LazyInit-first
invariant).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI/agent → daemon `tools/call` | Untrusted invocation crosses into the daemon; profile/mode authz MUST be enforced here, not in the bypassable CLI |
| session state → middleware | The daemon session's resolved AllowedTools is the authoritative whitelist; the middleware reads it via the shared getSession closure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-91-05 | Elevation of Privilege | read/ci-bot agent invokes a destructive edit verb once verbs are always-visible | mitigate | ProfileEnforcementMiddleware checks AllowedTools on every `tools/call` and refuses with typed PermissionDenied (Task 1) — THE load-bearing fix; do NOT defer |
| T-91-06 | Elevation of Privilege | enforcement middleware mis-ordered (runs after handler, or LazyInit no longer first) so authz is bypassed | mitigate | Install AFTER Guardrail and BEFORE LazyInit preserving LazyInit-first LIFO (Task 2); LIFO-order test fails on any reorder |
| T-91-07 | Spoofing / Tampering | a CLI-side-only verb filter is bypassed by a raw `tools/call` | mitigate | Authz is server-side in the daemon middleware (authoritative); the CLI's verb hiding (SEC-02, Plan 91-04) is UX only |
| T-91-08 | Information Disclosure | refusal message leaks other tools' existence | accept | the refusal names ONLY the requested tool + profile/mode (already public); it never enumerates other tools |
| T-91-09 | Tampering | a typed PermissionDenied returned as an IsError result instead of an error breaks `errors.Is` CLI-side | mitigate | return the error path (not IsError), asserted by the typed-error round-trip test (Task 1); the Guardrail Block path proves the wire round-trip |
| T-91-SC | Tampering | npm/pip/cargo installs | mitigate | zero new external packages; `serr` and the MCP SDK are already in-tree — no install task |
</threat_model>
