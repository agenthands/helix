## Honest scope limitations (stated, not defects)
1. **E2E composition inferred, not tested.** Each resolver's logic is unit-verified
   (fakeStore); the plumbing is real-store-verified (Phase 130, go only). The full
   production path — Phase-59 extraction → snapshot → `QueryEffectiveSymbolFact` →
   per-language resolver → `emit` → graph edge — is NOT exercised end-to-end for the
   four new languages (would need per-language source fixtures through the whole
   pipeline). Plumbing ✓ and resolver logic ✓ are each verified; their composition in
   production is [INFERENCE].
2. **Production cross-package cap is test-seam-gated.** `typeIndex` is nil in
   production (as for the pre-existing Go/Py/TS resolvers), so the D-13 intra-package
   cap fires only when a `typeIndex` is populated (tests). In production the resolvers
   emit at raw tier confidence without the cap. This is a **pre-existing Phase-62
   characteristic**, not new to v2.11 — stated for honesty.
3. **Heuristic (T6) is best-effort 0.45.** Idiomatic snake_case C rarely matches the
   camelCase suffix rules — honest low hit rate for C; the tier is a fallback.
4. **C `parseAnnotation` extracts primitives / function-pointers as the "type"**
   (`int x` → "int"; `void (*fp)(int)` → "void"), emitted at Tier-2 0.90 (red-team F2).
   Moot at close (typeIndex nil → Target=0; nothing emits pre-Phase-64; C's tier design
   is explicitly best-effort; the same primitive-as-type shape exists in the pre-existing
   Go/Py/TS resolvers). Deferred future hardening: a known-primitive allowlist so
   primitives fall through rather than emit a spurious 0.90 annotation edge. No code
   change at close — design-wide, out of v2.11 scope.
