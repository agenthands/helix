# SECURITY-REVIEW — v2.13 True intraprocedural DATA_FLOWS

## Verdict: PASSED

No critical/high/medium findings. No exploitable condition and no actionable
v2.13-introduced hardening item across the five threat checks. The change is a
pure-computation static-analysis extension: it reads the tree-sitter AST of the
user's own repo files (already the trust model for the 7 enabled languages),
derives opaque flow facts, and persists them via parameterized SQL. It adds no
file-write, network, exec, deserialization, reflection, `unsafe`, or new
dependency. One informational, out-of-scope, pre-existing note is recorded
below (does NOT affect the verdict).

Findings route to the architect; no code was edited (read-only analysis).

## Severity legend
critical/high = exploitable now · medium = conditional / defense-in-depth ·
low/tech_debt = hardening · none = clean.

## Check 1 — Path B extraction enablement (.rs/.kt/.php/.rb) — NONE (clean)

**Finding:** Enabling Rust/Kotlin/PHP/Ruby daemon extraction introduces **no new
trust boundary** the already-enabled 7 languages don't already have.

**Evidence:**
- The only change in `semantic_wiring.go` that touches extraction is `langFromExt`
  (`:1838`), a **pure extension→id map** — four new `case` arms returning constant
  language ids, no path logic (`semantic_wiring.go:1856-1863`: `.rs`→`rust`,
  `.kt/.kts`→`kotlin`, `.php`→`php`, `.rb`→`ruby`; guarded by
  `strings.ToLower(filepath.Ext(path))` at `:1839`, `default` returns `""` at
  `:1864-1865`). Unknown extensions still return `""` → "skip silently."
- The file-walk (`fullWalkPaths`, `semantic_wiring.go:1821`) is **unchanged** by the
  diff. `git diff -U6` shows the only hunk at that location is the doc comment above
  `langFromExt`; no `filepath.Join`, `os.*`, `Symlink`, or `EvalSymlinks` was added
  or altered → **no path-traversal / symlink-escape regression**.
- The 3 changed code files import no dangerous stdlib: a scan for
  `os`/`os/exec`/`net`/`reflect`/`unsafe`/`encoding/gob`/`ioutil` returned **NONE**.
  `summary.go` imports only `sort`, `strings`, and `go-tree-sitter`
  (`summary.go:20-25`) — the documented leaf-package boundary. The new daemon funcs
  use only `sort` + `fmt`.
- Downstream, the 4 new languages route through the **nil-resolver** path (see
  Check 5), so they add symbols/references/similarity/data_flows only — no
  has_type/uses_type surface. Trust model is identical to go/ts: parse a local
  repo file the user already chose to index.

**Verdict:** none. Same local-source tree-sitter parse as the existing 7 langs;
no new network/exec/file-write, no walk change, no path handling introduced.

## Check 2 — Fan-out / DoS in the two new emission passes — NONE (clean)

**Finding:** `inBodyDataFlowEdges` and `returnBridgeEdges` are **bounded and
linear in source size** (better than the plan's O(#params × #functions) upper
bound); directed dedup caps distinct edges; no unbounded recursion is introduced.

**Evidence:**
- `inBodyDataFlowEdges` (`semantic_similarity_edges.go:547-609`): iterates
  `withFlow` (finite subset of nodes, built at `:553-558`) × each node's
  `InBodyFlows` (a **dedup+sorted** slice — `summary.go:153` calls
  `dedupSortInBody`, bounded by the body's call-arg count, i.e. linear in AST
  size). A `seen map[[2]uint64]struct{}` keyed on `(prodNode, dstParam)`
  directed-dedups (`:590-594`). Every endpoint is gated: `nameCount != 1` skip
  (`:566,574`), `node == 0` skip (`:570,578`), arg-pos bounds check (`:583-585`),
  self-edge / zero-dst guard (`:587-589`). Global distinct-edge count ≤
  |functions| × |consumer-params| and ≤ total call-args across the repo —
  polynomial, no exponential term.
- `returnBridgeEdges` (`semantic_similarity_edges.go:621-667`): iterates the same
  sorted `withFlow` × each node's `Params` (bounded by the function's param count);
  `nodeToParams` is used for **lookup only** (`:636`, never ranged — confirmed by
  code + the `:617-620` doc), `seen` directed-dedups on `(srcParam, fnNode)`
  (`:648-652`), self-edge guarded (`:645`). Linear in total params.
- Engine recursion `walkFlow` (`summary.go:163-182`) recurses over
  `n.Child(i)` — a **finite, acyclic** tree-sitter parse tree. No manual cycle,
  no visited-set needed; depth = AST nesting depth. The auxiliary recursions
  (`collectOrigins.w` `:321-335`, `identText` `:363-376`, `findFirst` `:398-411`,
  `collectIdentNames.w` `:381-394`) are all tree-bounded. **v2.13 only threads an
  extra `*[]InBodyFlow` argument through the SAME pre-existing recursion**
  (diff hunk `walkFlow` signature + the two recursive-call sites) — it does not
  add a new recursive walk.
- No single small input yields super-linear output (no amplification); memory
  (the `seen` maps + edge slices) grows linearly with source, same shape as the
  pre-existing v2.9 `dataFlowEdges` pass.

**Verdict:** none. Bounded, directed-deduped, linear in AST size; the dedup
maps bound distinct edges; recursion is tree-finite and not new.

## Check 3 — Injection sink (EdgeFact.Reason from callee names) — NONE (clean)

**Finding:** `EdgeFact.Reason` for the new DATA_FLOWS edges is an **opaque
write-only** string. It is `fmt.Sprintf`'d from source-derived callee names,
persisted via **parameterized SQL**, and **never read/rendered/re-interpreted**
on any production output path.

**Evidence:**
- Construction: `fmt.Sprintf("return of %s -> %s param%d", ib.Producer,
  ib.Consumer, ib.ArgPos)` (`semantic_similarity_edges.go:604`) and
  `fmt.Sprintf("param%d -> return", pf.Index)` (`:662`). `%s`/`%d` verbs — the
  callee names are **arguments**, never a format string, so no format-string
  injection.
- Persistence: `WriteSnapshotFacts` inserts edges with a fully **parameterized**
  statement — `INSERT INTO semantic_edges (...) VALUES (?, ?, ...)` and
  `nullIfEmpty(e.Reason)` bound positionally (`snapshot.go:398-409`). No string
  concatenation into SQL → no SQLi.
- Rendering: a repo-wide `\.Reason\b` scan across `internal/daemon`,
  `internal/skill/semantic`, `internal/semantic` shows **every read of a
  DATA_FLOWS edge `.Reason` is test-only** (`dataflow_edges_test.go:243,280,385`).
  All other `.Reason` hits are unrelated structs (`ClusterStatus`/
  `RetrievalStatus` in `semantic_accessor_factories.go`, `ChainResponse` in
  `types/`, watcher `Status`, references `Reason` in `extract/to_store.go`).
- Output path proof: `trace_data_flow` returns only `{symbol_id, hops}`
  (`tools_trace_data_flow.go:41-46,149-164`); its result struct carries no edge
  `Reason` field. Reachability yields `SymbolID`+`Hops`, not edge reasons. No
  HTML/template/shell sink consumes `Reason`.

**Verdict:** none. Opaque stored string; parameterized write, no reader on the
render path — not concatenated into SQL/shell/template/format string.

## Check 5 — nil-resolver panic-safety (Path B relies on nil) — NONE (clean)

**Finding:** A nil resolver for the 4 new languages **cannot be dereferenced**;
it is guarded twice (construction gate + dispatch fallback). No nil-deref DoS.

**Evidence:**
- `newIndexedResolver` returns **nil** for rust/kotlin/php/ruby (they hit the
  `default:` arm — `type_resolver_wiring.go:89-91`).
- Guard #1 (construction): the registry only stores non-nil resolvers —
  `if res := newIndexedResolver(...); res != nil { reg[r.Language] = res }`
  (`type_resolver_wiring.go:190-192`). A nil resolver never enters `reg`.
- Guard #2 (dispatch): even if a ref's language has no registered resolver,
  `Dispatcher.resolverFor` returns `(nil, false)` (`resolver.go:159-169`) and
  `ResolveChain`/`ResolveSymbol` **early-return an unresolved 0.20 response
  without dereferencing** `r` (`resolver.go:173-185`, `189-201`). This is the
  documented D-12 invariant ("always emits a row, never errors").
- Reachability of the concern: `linkVarTypes` only emits a link when a symbol
  carries a non-empty `DeclaredType` (`semantic_vartype_link.go:47-49`), and
  `resolveTypeEdges` further drops any link whose `TypeName` is not a unique
  `nameToNode` key (`type_resolver_wiring.go:163-165`). So the 4 stub languages
  typically produce zero refs; and even a stray ref degrades to an unresolved
  response that `typeEdgeFromResponse` gates out at `resp.Target == 0`
  (`:264-266`). Group-level resolver errors are swallowed per-group
  (`:227-231`), never panicking the snapshot build.

**Verdict:** none. Nil is impossible to reach as a receiver; double-guarded,
fail-safe to an unresolved row.
