       `minisign -S -s internal/upgrade/testdata/test_keypair.key -m internal/upgrade/testdata/sample-archive.tar.gz -x internal/upgrade/testdata/sample-archive.tar.gz.minisig -W -t "helix-test-fixture"`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repo root → internal package | `minisign.pub` at repo root is the canonical key consumed by INSTALL.md curl-fetch ceremony; the package-local copy is what the binary embeds. Drift between the two is an integrity bug equivalent to a key swap. |
| CI workflow → release artifacts | The release.yml workflow is the chokepoint that produces signed binaries; any pre-flight gate that fails to actually run (e.g., misnamed target) silently lets a drifted key reach release. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-52-01-01 | Tampering | `internal/upgrade/minisign.pub` (build-time copy) drifts from repo-root `minisign.pub` and ships a mismatched key in the binary, breaking the upgrade-time signature verification chain — or worse, accepting a key the maintainer didn't intend | mitigate | `make verify-embed-pubkey` runs `cmp -s minisign.pub internal/upgrade/minisign.pub` and exits non-zero on any drift. The release.yml workflow gates the goreleaser run on this target, failing the release before any binary is signed. The same target is documented in the Makefile self-doc so contributors discover it on `make help`. |
| T-52-01-02 | Tampering | A contributor accidentally signs a real release with `internal/upgrade/testdata/test_keypair.key` — the test signing key escapes into a production verification flow | accept | The test keypair is generated with `untrusted comment: test-only` and lives in a clearly-named `testdata/` directory. The README.md in testdata states explicitly that this key cannot sign production releases (no infrastructure outside tests references it). Phase 51's CI pipeline uses `MINISIGN_PRIVATE_KEY` from GitHub Secrets — the testdata key has no path into that flow. |
| T-52-01-03 | Information Disclosure | Test fixtures (release JSON, sample archive) reference a real production URL and a network call leaks the test runner's IP | mitigate | The fixture uses `https://example.invalid/...` per RFC 6761 — guaranteed never to resolve. Tests using this fixture must override the base URL via httptest stub before any HTTP call (see Plan 04); a misconfigured test that tried to GET `example.invalid` would fail loudly with DNS errors, not silently leak. |
| T-52-01-04 | Denial of Service | The `verify-embed-pubkey` target is unreachable from the release workflow because the YAML edit landed under the wrong job, silently never running | mitigate | The verify command in this plan asserts `grep -v '^#' .github/workflows/release.yml | grep -q "make verify-embed-pubkey"` — the comment-stripped grep gate prevents the prose-in-comments self-invalidation pattern flagged in the planner critical rules. |
</threat_model>
