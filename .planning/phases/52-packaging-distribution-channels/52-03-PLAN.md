Without this plan, the renamed binary writes to `~/.serena/` and registers under `serena`, defeating the entire rename.
Output: a tree where `grep -rn 'SERENA_\|\.serena/' --include='*.go' --exclude-dir=legacy .` returns zero hits and the MCP server identifies as `helix` everywhere it touches a client.

This plan runs in Wave 2 because it edits files that Plan 02 just renamed (sharing `internal/cli/`, `internal/mcp/`, `internal/config/`); running it in parallel with Plan 02 would produce merge conflicts on shared `files_modified`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Renamed binary → external client config | `internal/cli/setup_clients.go` writes JSON payloads consumed by client CLIs (Claude, Cursor, etc.); a mismatched server-name field silently registers under the wrong identity and the client cannot find the MCP server. |
| Renamed binary → Claude Code hook scripts | Hook scripts live in the user's `.claude/` tree and execute on every session. Hooks invoking `serena <verb>` after the rename produce silent "command not found" failures with no diagnostic. |
| Renamed binary → user's existing config dir | Users who upgrade carry `~/.serena/` from previous versions; per D-02 (no fallback) the new binary reads `~/.helix/` exclusively. The orphaned `~/.serena/` is harmless but invisibly leaks disk if the user doesn't read CHANGELOG. |
