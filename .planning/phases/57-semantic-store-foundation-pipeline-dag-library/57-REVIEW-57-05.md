### BLOCKER

#### BL-01 — CR-01 fix is incomplete: absolute paths are still accepted, contradicting `StoreConfig.Path` doc

**Files:**
- `internal/semantic/store/duckdb.go:139-143`
- `internal/semantic/config.go:75-80`

**Issue:** The new path-traversal guard scans for `..` segments only:

```go
for _, seg := range strings.Split(filepath.ToSlash(path), "/") {
    if seg == ".." {
        return nil, fmt.Errorf("semantic.store.Open: path %q contains parent-reference segment (T-57-02-01): %w", path, serr.ErrInvalidArgs)
    }
}
```

`internal/semantic/config.go:75-80` still documents the contract as:

```go
// Path is workspace-relative (default: ".helix/semantic.duckdb").
// MUST be a relative path; absolute paths and `..` segments are rejected
// at Open time (T-57-02-01 mitigation).
```

A config like `path: "/etc/passwd"` (or any absolute path outside the workspace) splits into `["", "etc", "passwd"]` — none of those segments equal `..`, so Open falls through to `os.MkdirAll(filepath.Dir(path), 0o755)` and `sql.Open("duckdb", "/etc/passwd")`. The original CR-01 finding explicitly named both halves ("absolute paths AND `..` segments"); the executor closed only one half but did not adjust the doc.

This is the same code/doc mismatch that motivated the original BLOCKER classification — half-fixed. A security reviewer reading `StoreConfig.Path`'s doc will still believe absolute paths are rejected when they are not.

**Fix (pick one):**

(a) Honor the doc — also reject absolute paths:
```go
if filepath.IsAbs(path) {
    return nil, fmt.Errorf("semantic.store.Open: path %q must be workspace-relative (T-57-02-01): %w", path, serr.ErrInvalidArgs)
}
for _, seg := range strings.Split(filepath.ToSlash(path), "/") { ... }
```
…and decide what to do with the existing `TestOpen_AcceptsCleanRelativePath` which passes an absolute path returned by `t.TempDir()` as the "happy path" — that test would now fail. Either it has to switch to a workspace-rooted relative path, or option (b).

(b) Update the contract — drop "absolute paths" from the `StoreConfig.Path` doc and acknowledge the design is "caller joins workspace root, library refuses only `..` segments":
```go
// Path is workspace-relative by convention (default: ".helix/semantic.duckdb").
// `..` segments are rejected at Open time (T-57-02-01); absolute paths are
// trusted as caller-resolved.
```

Either path is acceptable; the current state — code rejects only `..`, doc claims it rejects both — is the BLOCKER.

### Warnings

#### WR-NEW-01 — `Probe.Reason` may leak internal DB error text into MCP tool output

**File:** `internal/kernel/health/tools.go:50-56`

**Issue:** When the bounded probe returns a non-deadline error, `ComputeSemanticStoreStatus` stuffs `err.Error()` directly into `SemanticStoreStatus.Reason`, and that struct is JSON-marshalled into the `get_health` response served to MCP clients (Claude Code, IDE assistants, CI bots). DuckDB and `database/sql` errors can include statement text, schema names, or driver-internal state. The Reason field is operator-helpful but doubles as a low-priority info-leak channel.

```go
if err := p.Probe(probeCtx); err != nil {
    reason := err.Error()
    if errors.Is(err, context.DeadlineExceeded) {
        reason = "probe_timeout"
    }
    return SemanticStoreStatus{State: "unhealthy", Reason: reason}
}
```

Today this is bounded because the probe is `SELECT 1` (no user-controlled SQL), but the daemon-side `semanticStoreProbe.Probe` *also* returns wrapped errors:

```go
// daemon.go:573-580
if p.s == nil {
    return fmt.Errorf("semantic store unavailable")
}
db := p.s.DB()
if db == nil {
    return fmt.Errorf("semantic store DB handle nil")
}
```

…so the reason field can carry text like `semantic store DB handle nil` or, more concerning, whatever `database/sql` surfaces when the underlying file is in a degraded state (potentially the configured path).

**Fix:** Either map known causes to a closed enum (`probe_timeout`, `nil_handle`, `db_error`) before assigning to Reason, or sanitize/truncate the error string. Pattern matches the closed-enum quarantine reasons already in `duckdb.go:75-80` (D-07).

#### WR-NEW-02 — Persistent transient reopen errors quarantine a healthy DB

**File:** `internal/semantic/store/duckdb.go:185-201`

**Issue:** The retry path looks correct on first read but conflates "transient on retry" with "corrupt":

```go
case reopenTransient:
    logger.Warn("semantic store reopen hit transient error; retrying once", ...)
    select {
    case <-time.After(250 * time.Millisecond):
    case <-ctx.Done():
        return nil, ctx.Err()
    }
    s, err2 := openExisting(ctx, path, label, logger, metrics)
    if err2 == nil {
        return s, nil
    }
    return quarantineAndRebuild(ctx, path, label, reasonCorruptFile, 0, logger, metrics)
```

If `err2` is itself transient (e.g., persistent EBUSY because a sibling daemon or backup process is holding the file), the code labels the workspace `reasonCorruptFile` and renames `<path>` to `<path>.corrupt.<unix-ts>`. That is data loss against a perfectly healthy DB whose only sin was a 250-ms-too-long lock contention window. The original WR-03 finding was "clean DBs lost to quarantine on transient EBUSY/EINTR"; the fix narrowed the window from "any error" to "any error after one retry," but the failure mode is still present.

**Fix:** Distinguish the second-attempt transient case. Two viable shapes:

(a) Tier-3 hard fail on retry-still-transient (preferred — supervisor can restart and try again):
```go
s, err2 := openExisting(ctx, path, label, logger, metrics)
if err2 == nil {
    return s, nil
}
if classifyReopenError(err2) == reopenTransient {
    return nil, fmt.Errorf("semantic.store.Open: transient errors persist across retry; refusing to quarantine clean DB: %w", err2)
}
return quarantineAndRebuild(ctx, path, label, reasonCorruptFile, 0, logger, metrics)
```

(b) Reclassify to a separate quarantine reason so the carve-out registry distinguishes corrupt-on-retry from transient-on-retry. (Requires updating the closed-enum carve-out per D-07; out of scope of v1.10 per the SUMMARY's reasoning that the enum is locked at four values.)

(a) is the minimum-friction fix and matches the existing forward-incompat short-circuit shape.

#### WR-NEW-03 — `noduckdb` analyzer test does not assert NO diagnostic on the sibling fixture

**Files:**
- `internal/lint/noduckdb/analyzer_test.go:20-22`
- `internal/lint/noduckdb/testdata/src/siblingpkg/imports.go`

**Issue:** The new test relies on a deliberate absence of a `//want` directive:

```go
func TestAnalyzer_AllowsSiblingNamespacePackage(t *testing.T) {
    analysistest.Run(t, analysistest.TestData(), noduckdb.Analyzer, "siblingpkg")
}
```

```go
// siblingpkg/imports.go
package siblingpkg
import _ "github.com/duckdb/duckdb-go-sibling"
```

`analysistest.Run` flags an UNEXPECTED diagnostic only when there's a `//want` comment somewhere; without ANY `//want` directive, an unexpected report from the analyzer surfaces as a test failure via `analysistest`'s implicit "no unexpected reports" check. This actually IS the documented behaviour of `analysistest` — but the test's correctness is non-obvious to a future maintainer. A bigger latent issue: the test does NOT prove the prefix-match form rejects `forbiddenImport+"/"` style false negatives. The fixture only imports `duckdb-go-sibling` (no slash subpath); a regression where the slash check is mistakenly removed (`path == forbiddenImport` only) would still pass this test because the existing `TestAnalyzer_RejectsImportFromBadpkg` covers the `/v2` reject case.

**Fix (low-cost):** Add a positive-assertion variant or a comment in `imports.go` documenting why no `//want` is present:

```go
// No //want directive: analysistest fails the test if the analyzer
// reports anything for this file, which is exactly the assertion this
// fixture is designed to make. See WR-02 closure in 57-05-PLAN.md.
```

…or extend the test to also import a `duckdb-go-sibling/v2` style subpath to lock the slash boundary against both directions.

#### IN-NEW-01 — `duckdb_winarm64.go` build-tag carve-out adds a `DB() *sql.DB` method that the SUMMARY flags as a deviation

**File:** `internal/semantic/store/duckdb_winarm64.go:37-39`

**Issue:** The plan didn't call out adding `DB()` to the windows/arm64 stub; the executor added it in 57-05 because the daemon-side `semanticStoreProbe.Probe` calls `p.s.DB()` and the stub would not compile without it. The SUMMARY logs this as deviation #3.

The fix (a nil-returning `DB() *sql.DB`) is correct and minimal — `Available()` already returns false on this target so `ComputeSemanticStoreStatus` returns `state="disabled"` long before `Probe` is called. But the contract is now slightly out of sync between the two files: `internal/semantic/store/duckdb.go:403-408` returns `nil` only when the receiver is nil; the windows/arm64 stub returns `nil` unconditionally. A future refactor that uses `DB()` as a "is store open" probe (instead of `Available()`) will silently mis-classify on this target.

**Fix:** Document the contract in both files. Add a one-line note next to the `Store` definition in `duckdb.go` ("`DB()` returns nil iff the store is not open; on windows/arm64 it always returns nil because this platform has no DuckDB build") so the cross-file invariant is discoverable.

#### IN-NEW-02 — Probe error path does not distinguish "store handle nil" (configuration bug) from "DB handle nil" (driver bug)

**File:** `internal/daemon/daemon.go:573-580`

**Issue:** Both branches return `fmt.Errorf` strings without sentinel wrapping. The `nil` cases are operationally distinct:

- `p.s == nil` means the daemon was started with `semantic_index.enabled=false` OR with a target that has no DuckDB (windows/arm64 stub). This is a **configuration** state, expected.
- `db == nil` (with `p.s != nil` but `p.s.Available() == true`) is theoretically unreachable today (Available implies db != nil per `duckdb.go:394`), but if it triggers it means the Store's internal invariant is broken.

Today the `Available()` check in `ComputeSemanticStoreStatus` short-circuits both cases to `state="disabled"` BEFORE Probe runs, so these strings are unreachable in practice. But the dead code is confusing — and if someone later forgets the `Available()` gate, the two error strings are indistinguishable to the operator.

**Fix:** Either remove the unreachable branch (`p.s == nil` is already gated by `Available()` returning false in that case) or wrap both with sentinel errors so the caller can distinguish (`serr.ErrUnsupported` for the config path, `fmt.Errorf(...)` only for the unexpected handle-nil case).

#### IN-NEW-03 — `TestApplyMigration001_RollsBackOnFailure` does not exercise the real bootstrap statement set

**File:** `internal/semantic/store/migrations_test.go:494-532`

**Issue:** The test injects three synthetic statements (`CREATE TABLE t1`, broken DDL, `CREATE TABLE t3`) to validate the rollback envelope. It does NOT pass `schema1Statements()` as the input, so a regression in `applyMigration001` itself (e.g., someone wires it back to use `db.ExecContext` directly, bypassing the new transactional path) would not be caught by THIS test.

The plan's RED→GREEN sequence is justifiable (the synthetic input deterministically fails mid-way without depending on the real schema), but the plan also did not add a paired "real migration also runs in a tx" assertion. The closest existing coverage is `TestMigration_Fresh_v2` / `_Existing_v2`, which exercise the happy path through `Open` but cannot detect "happens to be in a transaction" vs. "individual ExecContext calls" — both produce identical observable outcomes when no statement fails.

**Fix (cheap):** Add a one-line assertion that `applyMigration001` calls into `applyStatementsTx`, e.g., a grep-style reflection check, OR rename `applyMigration001` to `applyMigration001Statements` returning the slice and reroute. The SUMMARY's grep gate `grep -c 'applyStatementsTx' internal/semantic/store/migrations.go >= 5` is a reasonable proxy but is enforced outside the test runner. Acceptable for v1.10 scope; flagged for visibility.

## Notable strengths

- **JSON envelope is additive, not replacing.** The `SemanticStoreStatus` field embeds `*lspool.HealthReport` and adds `semantic_store` alongside — old MCP clients parsing only `workspaces` continue to work. Forward-compat win.
- **Boundary discipline holds.** Kernel/health does not import `internal/semantic`; the seam is the `SemanticStoreProbe` interface defined kernel-side and implemented daemon-side. Adheres to the project's hard architectural rule.
- **`classifyReopenError` is unit-tested in isolation** (`TestClassifyReopenError`) rather than via integration of the retry loop, which would be flaky. The TDD-skip rationale for the retry loop itself is well-documented in commit `6d20469f`.
- **`applyStatementsTx` is reusable** — extracting the BEGIN/COMMIT envelope from `applyMigration001` means future migrations can opt in (today only `001` uses it; `002` and `003` still use the bare ExecContext loop, by intentional design, since DuckDB ALTER TABLE has known DDL-in-tx quirks per `migrations.go:400-410`).
- **Path-traversal rejection uses `filepath.ToSlash` first**, which correctly normalizes Windows backslash separators before the segment scan. The fix is aware of cross-platform path syntax even though the file's build tag excludes windows/arm64.
- **5s budget for the schema-version probe matches the existing PingContext budget**, avoiding the introduction of a new constant. Consistent with the plan's TDD-skip rationale.
- **The sibling-namespace fixture** (`testdata/src/github.com/duckdb/duckdb-go-sibling/sibling.go`) compiles independently and is named so future grep audits will find it.
