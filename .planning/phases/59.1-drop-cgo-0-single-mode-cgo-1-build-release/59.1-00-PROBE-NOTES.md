### Variant probes attempted (defense-in-depth diagnostics)

Per RESEARCH §A1 fallback hint ("`-target aarch64-macos-none` newer zig
syntax variant") and the `--sysroot` SDK injection commonly recommended
for zig cc → darwin:

#### Variant A — `-target aarch64-macos-none`

```
$ CC="zig cc -target aarch64-macos-none" CGO_ENABLED=1 GOOS=darwin GOARCH=arm64 go build -o /tmp/helix-darwin-arm64-probe ./cmd/helix
process_collector_mem_cgo_darwin.c:18:10: fatal error: 'mach/mach_vm.h' file not found
exit=1
```

Same failure mode. The `-target …-none` suffix changes ABI/libc handling
but does NOT inject Apple's Mach kernel headers.

#### Variant B — `--sysroot=$(xcrun --show-sdk-path) -isystem ... -F ...`

Compile stage SUCCEEDED (Apple SDK headers reachable), but **link**
stage failed:

```
warning: unable to open library directory '/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/Users/Janis_Vizulis/go/pkg/mod/github.com/duckdb/duckdb-go-bindings/lib/darwin-arm64@v0.10502.0': FileNotFound
error: unable to find dynamic system library 'resolv' using strategy 'paths_first'. searched paths: none
error: unable to find dynamic system library 'duckdb_static' using strategy 'paths_first'. searched paths: none
error: unable to find dynamic system library 'duckdb_generated_extension_loader' using strategy 'paths_first'. searched paths: none
[... 19 more 'unable to find dynamic system library' errors for duckdb_* libs ...]
```

`go build` exit=1; no binary produced. **Diagnosis:** zig cc with
`--sysroot` rewrites bare `-L<absolute-path>` arguments as
`<sysroot><absolute-path>`, so the duckdb-go-bindings vendored
`/Users/Janis_Vizulis/go/pkg/mod/github.com/duckdb/duckdb-go-bindings/lib/darwin-arm64@v0.10502.0`
absolute path becomes nonsense. This is a known zig cc quirk
(<https://github.com/ziglang/zig/issues/3287> and follow-ups).

### Verdict: PROBE FAILS — Wave 2 darwin path is unsafe as planned

The two failure modes surfaced are **independent** of zig version
(0.14.1 vs 0.16.0) and **independent** of macOS-target syntax
(`aarch64-macos` vs `aarch64-macos-none`):

1. **Compile-time blocker:** `prometheus/client_golang/prometheus/process_collector_mem_cgo_darwin.c`
   `#include <mach/mach_vm.h>` is an Apple Mach kernel header that ships
   ONLY in the Apple SDK (`MacOSX*.sdk/usr/include/mach/`). zig cc's
   bundled libc does not include Mach kernel headers (and cannot legally
   redistribute them — Apple SDK headers carry an Apple license).
2. **Link-time blocker:** zig cc with `--sysroot` rewrites absolute `-L`
   paths against the sysroot prefix, breaking duckdb-go-bindings'
   vendored `lib/darwin-arm64@v0.10502.0` lookup. Even if (1) is solved
   by `--sysroot=$(xcrun --show-sdk-path)`, (2) is the next blocker.

**RESEARCH §A1 was incomplete:** it anticipated `FrameworkNotFound` link
errors but did not flag the `mach/mach_vm.h` compile error or the
zig-`-L`-sysroot-rewrite quirk. The "Helix links zero Apple frameworks"
assumption (A1) is technically true at the *Go level* but is invalidated
transitively through `prometheus/client_golang/prometheus`'s cgo darwin
process collector.

### Wave 2 contingency: ESCALATE TO DISCUSS-PHASE

**This probe BLOCKS Wave 2 (`.goreleaser.yaml` flip) until the planner
selects one of the following recovery paths.** No path is taken
unilaterally by this Wave 0 executor; per PLAN `<resume-signal>` "Type
'darwin contingency: <decision>' with the chosen path", the human
reviewer (or a `/gsd-discuss-phase 59.1` follow-up) owns the decision:

#### Recovery option (a) — Add a separate macOS runner for darwin builds

- **What:** Split `release.yml` into two jobs: `ubuntu-latest` for
  linux+windows zig cc cross-compile, `macos-latest` for darwin (uses
  Apple's clang against the Xcode SDK natively). goreleaser `--split`
  + workspace artifact stitch is the canonical pattern.
- **Pros:** Honors A1 ("canonical clang+SDK path on a macOS runner");
  no Apple SDK redistribution issues; no zig quirks; reproducibility
  gate still applies per-target.
- **Cons:** Breaks CONTEXT.md D-01 single-runner constraint EXPLICITLY
  recorded as a hard constraint. macOS runners are billed at 10× the
  Linux rate on GitHub Actions.

#### Recovery option (b) — Pin osxcross + Apple SDK on the Linux runner

- **What:** Install `osxcross` with a redistributable Apple SDK tarball
  (XCode 15.x SDK extracted to a Linux-mountable directory) and point
  zig cc at it via `--sysroot=/path/to/MacOSX.sdk`. Mitigate the
  `-L` sysroot-rewrite quirk by using zig's `-L` quoting workaround or
  switching to clang+ld64 once the SDK is mounted.
- **Pros:** Preserves D-01 single-runner. Pattern is well-established
  for Rust+Linux→darwin builds.
- **Cons:** Apple SDK redistribution license is **non-trivial** —
  redistributing the SDK tarball publicly violates Apple's developer
  license terms. The standard workaround is "build SDK tarball locally
  on a macOS host once, store it as a private CI secret, fetch in CI
  job". Adds operational complexity (SDK refresh on Xcode upgrades).

#### Recovery option (c) — Drop darwin from CGO=1; keep darwin on CGO=0 stubs

- **What:** Treat darwin as the Wave 1 windows-arm64 case — keep the
  `_nocgo.go` stubs alive for darwin only, leaving Phase 51.1 D-02 in
  effect for that target. Reduces the matrix to 4 CGO=1 archives
  (linux/{amd64,arm64} + windows/amd64) plus 2 CGO=0 darwin stubs.
- **Pros:** Smallest CI change; preserves D-01 single-runner.
- **Cons:** Massively undermines the entire phase's premise ("drop
  CGO=0 stubs"). Phase 59.1 stops being a single-mode CGO=1 release.
  Likely requires re-scoping the phase or splitting into 59.1a / 59.1b.

#### Recovery option (d) — Vendor `prometheus/client_golang` shim

- **What:** Replace the `process_collector_mem_cgo_darwin.c` import
  path with a Go-only fallback that reports zero memory metrics on
  darwin (or upstream a `//go:build !cgo || darwin_no_mach` shim).
  Most darwin processes don't need Mach VM precision metrics in
  prod.
- **Pros:** Side-steps the Apple SDK issue entirely; no CI changes.
- **Cons:** Sustained vendor maintenance burden; observability
  regression on darwin (process_resident_memory_bytes coarsens);
  upstream PR uncertain.

**Recommended:** option (b) **osxcross + private-secret SDK** is the
industry-standard path; option (a) is the cheapest engineering effort
but contradicts D-01. Option (c) is the least-bad fall-back if (a)
and (b) are both vetoed. Option (d) is a long-tail upstream fix that
should be opened in parallel regardless.
