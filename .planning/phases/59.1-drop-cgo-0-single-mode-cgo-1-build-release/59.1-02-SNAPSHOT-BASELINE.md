## Note (FALLBACK-B + .tar.gz archives)

Under the multi-build-entry refactor (FALLBACK-B per 59.1-02-SPLIT-PROBE-NOTES.md),
`goreleaser release --snapshot` (which is what `make release-snapshot` invokes)
attempts to build BOTH `helix-non-darwin` and `helix-darwin` entries from a single
goreleaser invocation, because the OSS CLI lacks the GoReleaser-Pro-only `--split`
mechanic to constrain a runner to a single build entry. On a darwin host, the
`helix-non-darwin/windows_amd64_v1` link step fails at `zig cc` link time with
C++ stdlib undefined symbols (libduckdb_static.a was built against libstdc++ but zig
defaults to libc++; lld-link cannot resolve the cross-stdlib symbols). This is a
**darwin-host-specific local-build limitation**, not a config defect — the
ubuntu-22.04 CI runner does not hit it because it invokes
`goreleaser build --id helix-non-darwin` (only the non-darwin entry).

The canonical FALLBACK-B local-on-darwin invocation per
59.1-02-SPLIT-PROBE-NOTES.md is therefore `goreleaser build --id helix-darwin`,
which produces **binaries** (no `.tar.gz` archives — `goreleaser build` does
not run the archive pipe). `.tar.gz` archives are produced in CI by the merge
job's `goreleaser release --skip=build` invocation, which assembles archives
from the per-runner uploaded binaries. This baseline records the **binary**
sha256s + sizes as the partial-matrix audit artifact.

For Wave 4's CONTRIBUTING.md "Releasing" section, document this caveat: on a
darwin contributor box, `make release-snapshot` will fail at the
`helix-non-darwin/windows_amd64_v1` link step. The actionable local invocation
on a darwin host is `goreleaser build --snapshot --clean --id helix-darwin`
(produces 2 darwin binaries; no archives). On a linux contributor box (with
zig 0.14.1+ installed), `goreleaser build --snapshot --clean --id
helix-non-darwin` produces 4 linux+windows binaries.
