## Probe verdict (Task 1)

The Wave 2 prerequisite probe (RESEARCH Open Question #6 + Risks > MEDIUM A11) discovered that the GoReleaser **split-and-merge mechanic** (`partial.by_target` config + `goreleaser release --split` + `goreleaser continue` / `release --merge`) is **GoReleaser Pro exclusive**. Verbatim from `https://goreleaser.com/customization/partial/`:

> "With GoReleaser Pro, you can split and merge goreleaser release runs. This feature is exclusively available with GoReleaser Pro."

`goreleaser v2.15.4` is a bug-fix patch on top of v2.15.3 (six `fix(...)` commits, no new commands or schema). Local probe of v2.15.3 OSS:

```
$ goreleaser --help 2>&1 | grep -iE 'split|merge|continue'
(no matches)
$ goreleaser release --help 2>&1 | grep -iE 'split|merge'
(no matches)
```

The OSS top-level command set is `{build, check, completion, healthcheck, help, init, jsonschema, release}` — no `continue` subcommand, no `--split` / `--merge` flag on `release`.

**Path chosen: FALLBACK-B-MULTI-BUILD-ID.** FALLBACK-A (bump pin) was rejected because Pro is a paid commercial license, not a different OSS tag. Bumping any v2.x OSS tag would not unlock the feature.

## Deviations from Plan

### 1. [Rule 1 — Bug] Plan Task 4 archive-count check assumed Path-A; under FALLBACK-B `goreleaser build` does not produce archives

- **Found during:** Task 4 (local snapshot run)
- **Issue:** The plan's Task 4 `<verify>` and `<acceptance_criteria>` blocks expected `helix_v*_*.tar.gz` files in `dist/` and counted them. Under FALLBACK-B the canonical local invocation is `goreleaser build --id <id>`, which produces **binaries** (no archive pipe run); only the merge job's `goreleaser release --skip=build` produces the `.tar.gz` archives, and the merge job runs in CI, not locally.
- **Fix:** Wrote the baseline file using **binary** sha256s + sizes (still ≥2 sha256 lines per the verify regex), and explicitly documented the FALLBACK-B-on-darwin caveat. The plan's `<verify>` `automated` block (`grep -cE '^[0-9a-f]{64}' ... -ge "2"`) still passes because sha256-line-count is the substantive criterion, not archive-file-count.
- **Files modified:** `.planning/phases/.../59.1-02-SNAPSHOT-BASELINE.md`
- **Commit:** `c537d25b`

### 2. [Rule 2 — Critical Functionality] On a darwin host, `make release-snapshot` will fail at helix-non-darwin/windows_amd64_v1 link step

- **Found during:** Task 4 (local snapshot run)
- **Issue:** `make release-snapshot` invokes `goreleaser release --snapshot --clean --skip=sign`, which builds BOTH `helix-non-darwin` and `helix-darwin` entries from a single goreleaser invocation (because the OSS CLI lacks `--split` to constrain to a single entry). On a darwin host the helix-non-darwin/windows_amd64_v1 build fails at zig cc link time with C++ stdlib undefined symbols (`std::ostream`, `std::basic_streambuf`, `std::rethrow_exception` etc) because libduckdb_static.a was built against libstdc++ but zig defaults to libc++. lld-link cannot resolve cross-stdlib symbols.
- **Fix:** Documented in `59.1-02-SNAPSHOT-BASELINE.md` under "Note (FALLBACK-B + .tar.gz archives)". This is a **darwin-host-specific local-build limitation, NOT a config defect**. CI ubuntu runner does not hit it because it invokes `goreleaser build --id helix-non-darwin` (constrained to non-darwin entry). Wave 4 picks up the canonical FALLBACK-B per-host invocations for CONTRIBUTING.md "Releasing":
  - darwin host: `goreleaser build --snapshot --clean --id helix-darwin` (2 binaries)
  - linux host: `goreleaser build --snapshot --clean --id helix-non-darwin` (4 binaries)
- **Files modified:** `.planning/phases/.../59.1-02-SNAPSHOT-BASELINE.md`
- **Commit:** `c537d25b`
- **Hand-off:** Wave 4 deviation note for CONTRIBUTING.md prose.

Architectural intent of D-15 preserved entirely; only the syntactic mechanism differs. FALLBACK-A rejected because GoReleaser Pro is a paid commercial license, not a different OSS tag.
