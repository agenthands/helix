## Summary

Phase 59.1 is a release-pipeline inversion: flip Phase 51.1 D-02 (the daemon's `treesitter.Available` refusal under CGO=0) to the opposite invariant — single-mode CGO=1 — and re-wire the goreleaser path to compile all 6 archives under CGO=1 on a single `ubuntu-22.04` runner using `zig cc` as a hermetic cross-compiler. The reproducibility gate (Pass-1 ≡ Pass-2 byte-identical, lines 42–121 of `release.yml`) is preserved verbatim and continues to gate the real release pass.

The deletion side is mechanical and well-understood: 12 `_nocgo.go` files (CONTEXT.md says 9; HEAD has 12 — see Files-to-touch), one `_nocgo_test.go` file (also new since CONTEXT.md was written), the `treesitter.Available` constant, the daemon step-6a refusal block, and `//go:build cgo` tags on 24 production + test files. The `_cgo.go` siblings flatten to plain `.go`. The lone `migrations_registry_cgo.go` (no nocgo sibling) also flattens to `migrations_registry.go`. The locally-vendored R/Swift bindings already lost their `binding_nocgo.go` siblings before this phase began (Phase 51.1 cleanup), so D-05's "fold into D-05?" question for them is moot — they only need their `//go:build cgo` tag stripped from `binding.go`.

The release-flip side has one known structural concern (windows-arm64 + duckdb-go-bindings, see Risks) and one well-precedented pattern: the canonical `goreleaser/example-zig-cgo` repository at `github.com/goreleaser/example-zig-cgo` uses precisely the shape this phase needs (`mlugg/setup-zig@d1434d08867e3ee9daa34448df10607b98908d29 # v2.2.1`, conditional Go-template `env:` block setting per-target `CC=zig cc -target ...`, native clang+SDK for darwin). For Helix the darwin path can use zig cc instead of clang+SDK because Helix's tree-sitter usage links zero Apple frameworks (verified by grep — pure C parsers in `internal/treesitter/bindings/{r,swift}/src/`), making zig-cc-for-darwin the simplest hermetic approach.

**Primary recommendation:** Pin **`mlugg/setup-zig@d1434d08867e3ee9daa34448df10607b98908d29  # v2.2.1`** with **`zig version: 0.14.1`** (released 2025-05-21, ~12 months of bake time; 0.16.0 just released 2026-04-13 and is too fresh for a reproducibility-gated release pipeline). Use **goreleaser v2 templated `env:` block** (not `overrides:`) for per-target `CC=zig cc -target <triple>` because the canonical example uses it and it keeps the build matrix readable in one block. Use **musl libc for linux** and **gnu for windows** (matches the canonical example and avoids glibc-version-bound binaries). Use **macos for darwin** (`zig cc -target x86_64-macos / aarch64-macos` — no minimum-OS pin needed; tree-sitter's pure C does not link any Apple framework, so the `FrameworkNotFound` issue chain that drove the canonical example to clang+SDK does NOT apply here).

### Pattern 1: goreleaser per-target CC via templated env:

**What:** A single `builds[].env:` block uses Go template conditionals to set `CC=zig cc -target <triple>` based on `{{ .Os }}` and `{{ .Arch }}`.
**When to use:** Cross-compiling a single Go module to multiple {goos,goarch} pairs with cgo, where each target needs a distinct C toolchain.
**Why this over `overrides:`:** Single readable block; matches the canonical `goreleaser/example-zig-cgo` shape; one diff hunk in `.goreleaser.yaml` instead of six.
**Example:**
```yaml
# Source: https://raw.githubusercontent.com/goreleaser/example-zig-cgo/master/.goreleaser.yaml
# Adapted for Helix: musl for linux, gnu for windows, macos for darwin (no Apple frameworks linked).
builds:
  - id: helix
    main: ./cmd/helix
    binary: helix
    env:
      - CGO_ENABLED=1
      - GOFLAGS=-mod=readonly
      - >-
        {{- if eq .Os "linux" }}
          {{- if eq .Arch "amd64" }}CC=zig cc -target x86_64-linux-musl{{- end }}
          {{- if eq .Arch "arm64" }}CC=zig cc -target aarch64-linux-musl{{- end }}
        {{- else if eq .Os "windows" }}
          {{- if eq .Arch "amd64" }}CC=zig cc -target x86_64-windows-gnu{{- end }}
          {{- if eq .Arch "arm64" }}CC=zig cc -target aarch64-windows-gnu{{- end }}
        {{- else if eq .Os "darwin" }}
          {{- if eq .Arch "amd64" }}CC=zig cc -target x86_64-macos{{- end }}
          {{- if eq .Arch "arm64" }}CC=zig cc -target aarch64-macos{{- end }}
        {{- end }}
    goos: [darwin, linux, windows]
    goarch: [amd64, arm64]
    flags: [-trimpath, -buildvcs=false]
    ldflags:
      - -s -w
      - -X main.version={{.Version}}
      - -X main.commit={{.Commit}}
      - -X main.date={{.CommitDate}}
    mod_timestamp: '{{ .CommitTimestamp }}'
```
Note: the `-lc` suffix that `goreleaser/example-zig-cgo` adds is for that example's specific cgo deps (likely sqlite3 native). For Helix, `zig cc -target ...` should suffice without the explicit `-lc` — zig's libc bundling is automatic per target. The plan should test with and without `-lc` if Pass-1/Pass-2 reproducibility surfaces a divergence.

### Pattern 3: Tool-presence detection in Makefile

**What:** A `command -v <tool> >/dev/null 2>&1 || { echo "<tool> not installed; <hint>"; exit 1; }` guard at the top of a Make recipe.
**When to use:** A make target depends on a tool that is not in `go.mod` and not pre-installed by `setup-go`.
**Example:**
```makefile
# Source: existing Makefile lines 56-58 (release-snapshot target — verbatim style).
release-snapshot: ## Run a local goreleaser dry-run; writes archives to dist/ (overwrites; gitignored)
	@command -v goreleaser >/dev/null 2>&1 || { \
	  echo "goreleaser not installed; see CONTRIBUTING.md (Releasing). brew install goreleaser"; exit 1; }
	@command -v zig >/dev/null 2>&1 || { \
	  echo "zig not installed (required for CGO=1 cross-compile); see CONTRIBUTING.md (Releasing). brew install zig (macOS) or apt install zig (Ubuntu 22.04+)"; exit 1; }
	goreleaser release --snapshot --clean --skip=sign
```
The `make build` target is unchanged — local dev uses host CC.

### Anti-Patterns to Avoid

- **Soften the reproducibility gate** if Pass-1 ≡ Pass-2 fails on first CGO=1 run. CONTEXT.md D-10 explicitly rejects "Pass-3-style limitation" framing. Investigate via the WR-07 forensic dump (already in release.yml lines 88-119) and add zig flags (`-fdebug-prefix-map`, `ZIG_GLOBAL_CACHE_DIR` pin, `-Wl,--build-id=none`) instead.
- **Add `_nocgo.go` stubs back** if any future v1.10 phase (60/61/62) hits a "but my cgo type leaks into a CGO=0 caller" situation. The point of 59.1 is that those situations now hard-fail at `go build` and are fixed by changing the code, not by stubbing.
- **Use goreleaser's `builder: zig`** — that's for native Zig sources, not Go+cgo. Stay on the default Go builder.
- **Add a separate `make release-smoke` target** for the linux-amd64 daemon smoke (D-04). Folding it into `release-snapshot` would mix the dry-run-build concern with the runtime-smoke concern. Recommend a NEW `make release-smoke` target with one-line help annotation, mirroring the `bench` / `bench-baseline` self-doc style.
- **Renumber daemon bootstrap steps** after deleting 6a. Phase 57 already established that the numbering is "forward-only despite non-monotonic" (cited in v1.10-MILESTONE-AUDIT). Leave 6b → 6c → 6d as they are; just delete 6a's block. Prevents a useless test-file diff (`daemon_grammar_test.go` doesn't reference step numbers but every reader who memorized the comment indexes does).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Zig install on a CI runner | shell `curl ... && tar xJf` | `mlugg/setup-zig@<sha>` | Pinned action gives cache + integrity; rolling our own is the WR-04 anti-pattern (every WR-04/WR-07 lesson Phase 51/58 learned applies here) |
| Per-target CC env management | Six separate `goos:` × `goarch:` build entries each with its own `env:` | Single templated `env:` block | Canonical pattern; lower diff; same end-state |
| Reproducibility-gate replacement | Replace Pass-1/Pass-2 with a hash committed in-repo | Keep the existing gate verbatim | Already proven over Phase 58 rc1.0 → rc1.3 cycle; soft-coding the expected hash defeats the point |
| Linux-amd64 daemon smoke harness | New test fixture under testdata/ | Reuse `testdata/fixtures/go/main.go` | Already exists; already used by integration tests; smallest blast radius |
| Doc sweep tooling | A new `cmd/doc-sweep` analyzer | Manual `grep -rn 'CGO=0\|no CGO\|CGO_ENABLED=0'` + Edit | Six docs, sub-50-line diffs each; analyzer overhead is not worth it for one-shot work |

**Key insight:** The phase has TWO surfaces — *deletion* (mechanical, low-risk, well-bounded) and *release-pipeline flip* (one well-precedented pattern + one critical unknown). Don't conflate them in plans. The deletion can land first as Wave 1; the goreleaser flip + zig pin lands as Wave 2; reproducibility validation gates everything else as Wave 5.

## Common Pitfalls

### Pitfall 1: Reproducibility-gate divergence on first CGO=1 run

**What goes wrong:** Pass-1 sha256 ≠ Pass-2 sha256 because zig cc embeds a build-time path or random ordering into one of the C objects.
**Why it happens:** Native C compilation injects more non-determinism than pure Go (file paths in __FILE__ macros, debug section ordering, build-id linker stamps).
**How to avoid:**
1. Pin zig to a single exact version (D-02 — already mandatory).
2. Pin `ZIG_GLOBAL_CACHE_DIR` to a stable per-job path inside `release.yml` if cache misses cause divergence (e.g. `ZIG_GLOBAL_CACHE_DIR=$RUNNER_TEMP/zig-cache`).
3. The Go-side flags `-trimpath` and `-buildvcs=false` are already there.
4. If still divergent, add `-fdebug-prefix-map=$PWD=.` to `CGO_CFLAGS` to neutralize embedded paths.
5. If still divergent, add `-Wl,--build-id=none` (linux/windows) to neutralize build-id stamps.
**Warning signs:** The WR-07 forensic dump in release.yml (lines 88-119) is the diagnostic. It surfaces per-file sha256 diffs, tar entry metadata diffs, gzip header bytes, and `go version -m` output diffs. The first divergent file's sha256 plus `go version -m` will tell you whether the diff is in Go-managed metadata, C-side debug info, or archive-level (gzip mtime / tar order).

### Pitfall 2: windows-arm64 build fails because duckdb-go-bindings has no prebuilt static library for that target

**What goes wrong:** `goreleaser build` for `windows/arm64` fails at the Go link stage with "missing duckdb library for windows-arm64".
**Why it happens:** Documented above — duckdb-go-bindings/lib/ ships {darwin-amd64, darwin-arm64, linux-amd64, linux-arm64, windows-amd64} but NOT windows-arm64 [VERIFIED: https://github.com/duckdb/duckdb-go-bindings, fetched 2026-05-04].
**How to avoid:** Pick a resolution path BEFORE execution (see Risks). The planner CANNOT defer this; the windows-arm64 archive will fail on first CI run otherwise.

### Pitfall 3: zig binary not found on contributor's path during `make release-snapshot`

**What goes wrong:** Contributor runs the dry-run, gets a goreleaser error mid-build instead of a clean upfront failure.
**How to avoid:** Pattern 3 above — add a `command -v zig` guard at the top of the `release-snapshot` Makefile recipe (D-03).

### Pitfall 4: Stale `dist-pass-1/` from a prior local run feeds back into a comparison

**What goes wrong:** Local `make release-snapshot` after a partial run leaves `dist/` from a previous build; if the new build resolves to a *different* binary, the contributor sees a false "non-reproducible" diff.
**How to avoid:** `goreleaser release --snapshot --clean ...` (note `--clean`) already wipes `dist/` per invocation. Document this in CONTRIBUTING.md anyway — contributors who run two separate `goreleaser` invocations themselves (without `--clean` between) can hit this.

### Pitfall 5: Test files with `//go:build cgo && integration` (one such file exists)

**What goes wrong:** Mass-stripping `//go:build cgo` regex-style leaves `//go:build  && integration` (note the double space and dangling `&&`), which is a build-tag syntax error.
**Where:** `internal/daemon/daemon_semantic_test.go:1` has `//go:build cgo && integration`.
**How to avoid:** This is a SED gotcha. The plan's tag-strip task must specifically handle the compound case. Recommend just listing all 24 files and handling them individually rather than running a regex pass. Concrete rewrite: `//go:build cgo && integration` → `//go:build integration`. (One file. One Edit. No regex.)

### Pitfall 6: `treesitter.Available` referenced from a doc comment in a stub file we're deleting anyway

**What goes wrong:** After deleting `treesitter.Available` and the daemon block, a stale doc comment in `duckdb_nocgo.go` still says "mirrors the treesitter.Available pattern" → grep audit fails.
**Where:** `internal/semantic/store/duckdb_nocgo.go:30` and `internal/semantic/store/duckdb_nocgo_test.go:34`.
**How to avoid:** These two files are DELETED in the same wave, so the references vanish with them. Verify with `grep -rn 'treesitter.Available\|treesitter\\.Available' .` after the deletion task completes — should return zero hits across all of `internal/`, `cmd/`, and `.planning/` (apart from the 51.1-CONTEXT.md / SUMMARY.md historical record, which is intentional).

## Risks & Unknowns

### CRITICAL — windows-arm64 has no prebuilt duckdb-go-bindings library

**The block:** `github.com/duckdb/duckdb-go-bindings/lib/` ships {darwin-amd64, darwin-arm64, linux-amd64, linux-arm64, windows-amd64}. No `lib/windows-arm64`. Helix's `go.mod` reflects this (the 5 listed indirect deps verified 2026-05-04). Under the post-flip CGO=1 build, the windows-arm64 archive will fail at the link stage.

**The four resolution paths** (planner picks ONE before execution):

1. **Drop windows-arm64 from the 6-archive matrix.** Pros: simplest; ~30-line `.goreleaser.yaml` change (remove `arm64` from the windows entry; add a separate `windows: [amd64]` build entry; rebalance `archives:` IDs). Cons: breaks the "6 archives" framing in CONTEXT.md `<deferred>` ("Reducing supported platforms — keeping all 6 archives is the explicit choice"). User explicitly said "if zig cc cannot reach a target reliably (e.g. windows-arm64 in some zig versions), researcher flags it as a phase-execution blocker, not as a deferred idea." This is the closest phrasing to "drop" but it's not exactly that — it's "duckdb-go-bindings doesn't reach", not "zig doesn't reach". **NOT RECOMMENDED** unless paths 2-4 are infeasible.

2. **Build duckdb static library from source for windows-arm64 in a separate goreleaser hook step.** Pros: keeps all 6 archives; uses the documented `duckdb_use_static_lib` build tag. Cons: adds significant CI complexity (cross-compile DuckDB's massive C++ codebase to windows-arm64 from linux runner, linking against `-lws2_32 -lwsock32 -lrstrtmgr -lstdc++ -lm --static`); reproducibility risk multiplied; phase scope balloons. **NOT RECOMMENDED** for a 1-week phase.

3. **Stub the semantic store for windows-arm64 only via a build tag.** Add `//go:build !(windows && arm64)` to `internal/semantic/store/duckdb.go` and ship a `duckdb_winarm64.go` stub (matching the old `_nocgo.go` shape but gated on the platform tuple, not on cgo). The phase becomes "single-mode CGO=1 EXCEPT the semantic store on windows-arm64". User explicitly requested NO `_nocgo.go` accumulation; this is structurally different (it's `_winarm64.go`, not `_nocgo.go`) but spiritually similar. Pros: keeps all 6 archives functional except for `semantic_index` on windows-arm64; small diff; reversible when upstream ships the library. Cons: re-introduces a platform-specific stub apparatus that the phase exists to delete. **MAYBE RECOMMENDED.** Discuss with user.

4. **Drop windows-arm64 with documentation pointing at duckdb-go-bindings upstream issue tracker.** Same as path 1 but adds a deferred-item entry tracking the windows-arm64 restoration as a future phase contingent on duckdb-go-bindings shipping the missing library. Pros: simplest forward action; clean honest scope. Cons: 6-archive matrix becomes 5. **POSSIBLY RECOMMENDED** if path 3 feels like a regression on the spirit of the phase.

**Recommendation:** **Path 3 (platform-tag stub for semantic_index on windows-arm64)** with a clear deferred-item entry tracking restoration once `duckdb-go-bindings/lib/windows-arm64` ships upstream. Reasoning: it preserves the 6-archive matrix, preserves the single-mode CGO=1 invariant for all *other* targets (the stub is platform-tagged, not CGO-tagged), and the `_winarm64.go` shape is honest about its scope. The user's spirit — "no more accumulating CGO=0 stubs in v1.10 phases" — is preserved because the stub is *platform*-conditional, not *CGO*-conditional.

**Action required:** Add this as a phase-execution-blocker item that the discuss-phase or planner must explicitly resolve via user signoff before the goreleaser flip wave starts. Without resolution, Wave 2 of the plan cannot execute.
