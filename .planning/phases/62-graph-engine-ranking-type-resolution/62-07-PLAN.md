Close 62-VERIFICATION.md gap CR-01 (truth #N "RankScheduler.runIncrementalRepair holds the per-workspace overlay lock across CountStaleScoreRows callback — latent self-deadlock").

`runIncrementalRepair` at `internal/semantic/graph/scheduler.go:237-296` acquires `release := s.store.LockWorkspace(s.repoID)` with `defer release()` (line 238). The function calls `tx.Commit()` at line 271 and at line 282 invokes `s.store.CountStaleScoreRows(ctx, ...)` while the workspace lock is STILL held (defer runs only at function return). Today the production `rankStoreAdapter.CountStaleScoreRows` (`internal/daemon/rank_wiring.go:264-268`) is a no-op stub returning `0,0,nil` so the deadlock is dormant. The moment Phase 64 wires a real CountStaleScoreRows (or any future read path takes the same per-workspace lock), this becomes a hard self-deadlock against itself — the same per-workspace mutex `BeginRepairTx` / `BeginOverlayTx` use is held across the call.

The fix is structural: drop the `defer`, release explicitly after `tx.Commit()` and before the post-commit stale-fraction probe, AND document the contract on `SchedulerStore.CountStaleScoreRows` so future implementations cannot reintroduce the hazard by convention drift.

Purpose: Convert a latent self-deadlock into structural unreachability ahead of Phase 64's real CountStaleScoreRows implementation. Lock the contract on SchedulerStore so the convention is enforced by structure (explicit lock release at the call site) rather than by callee discipline.

Output: Reordered lock-release sequence in `runIncrementalRepair`, lock-free contract documented on the interface, and a contract test that wraps SchedulerStore in a stub whose CountStaleScoreRows attempts to re-acquire LockWorkspace under a tight ctx-deadline — RED today (test deadlocks / hits deadline), GREEN after the reorder.
