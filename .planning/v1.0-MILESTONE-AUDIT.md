# v1.0 Milestone Audit Report

## Executive Summary

All 4 phases pass individual verification with 68/68 requirements satisfied at the code level. However, **cross-phase integration reveals a systemic gap**: the daemon bootstrap (`daemon.go`) was built in Phase 1 with placeholder tools and was **never updated** in Phases 2-4 to wire in the kernel, tools, skills, or profiles.

**Result:** The production binary starts a daemon that responds only to `ping`, `echo`, and `activate_project`. All 30+ real tools (symbol retrieval, editing, file ops, diagnostics, memory, workflow, profiles) exist as compiled, tested code but are **unreachable from the production entry point**.

47 of 68 requirements (69%) have correct implementations that are disconnected from the runtime.

## Integration Gaps (Critical)

### 1. Daemon Does Not Create Kernel or Wire Tools

**Root cause:** `internal/daemon/daemon.go` creates only `workspace.Registry` and `SerenaMCPServer` with 3 dummy tools. It does NOT instantiate `kernel.Kernel`, call any `RegisterTools()` function, or wire skill-provided tools.

**Impact:** 30+ MCP tools unreachable. Affects: SYM-01..09, EDT-01..06, FIL-01..06, DGN-01..03, DMN-07..11, WRK-02..03

### 2. Skill init() Imports Missing

**Root cause:** Skills register via Go `init()` side effects. No blank imports (`_ "internal/skill/memory"`) exist in the import chain from `main()`. Skill registry is empty at runtime.

**Impact:** Memory, workflow, and profile tools never register. Affects: MEM-01..05, WFL-01..03, PRF-01..05

### 3. Pool Does Not Use Installer

**Root cause:** `lspool/pool.go` uses `entry.Command` directly to spawn workers. Never calls `langregistry.Installer.Resolve()` which implements the three-tier PATH/download/error strategy.

**Impact:** Language servers must be pre-installed in PATH; auto-download never triggers. Affects: LNG-02

### 4. Skill Names Mismatch in Profiles

**Root cause:** Profile YAMLs reference `symbol-retrieval`, `symbol-editing`, `diagnostics`, `file-ops` skills that don't exist. Only `memory`, `workflow`, `profile` are registered. `skill.ResolveTools()` will find zero tools for 4/6 skill categories.

**Impact:** Mode switching produces incomplete tool sets. Affects: PRF-01, PRF-02, PRF-03

### 5. Skill ToolDef RegisterFn No-Op

**Root cause:** All skill-provided `mcp.ToolDef` instances have `RegisterFn: func(server interface{}) error { return nil }`. Even if wired, tools won't be added to the SDK server.

**Impact:** Skill tools (memory, workflow) cannot be registered via current mechanism. Affects: MEM-01..05, WFL-01..02

### 6. ResolveProfile Never Called

**Root cause:** `config.ResolveProfile()` exists but is never called from `runDaemon()`. The `--profile` CLI flag is accepted and stored but never applied.

**Impact:** Profile-based tool filtering never activates. Affects: PRF-05

## Root Cause Analysis

The integration gap has a single root cause: **each phase built its components in isolation and registered them with interfaces/functions designed for daemon-level wiring, but no phase included the daemon bootstrap updates to actually call those registration points.**

Phase 1 built the daemon skeleton with placeholder tools. Phases 2-4 built real tools with `RegisterTools()` functions and `skill.Register()` init() hooks. But the daemon's `New()` and `Run()` functions were never updated to:

1. Create `langregistry.NewRegistry()`
2. Create `kernel.NewKernel(...)` 
3. Call `RegisterTools()` for symbols, edit, fileops, diag
4. Import skill packages for init() side effects
5. Call `skill.InitAll(deps)` 
6. Wire skill tools to MCP SDK
7. Install `ProfileFilterMiddleware`
8. Call `config.ResolveProfile()`

This is a **single integration phase** worth of work — all building blocks exist and are individually tested.

## Recommendation

Status: **gaps_found** — critical integration gaps prevent the binary from exposing any real functionality.

The fix is a focused daemon bootstrap wiring phase that connects existing, tested components. No new features needed — purely orchestration code.
