## BLOCKER 1 — CGO=0 build broken by Phase 59

**Affects:** REL-01 (cosign release pipeline), STORE-06 (CGO=0 stub principle), EXTRACT-01..05 (Phase 59 packaging).

**Symptom:**
```
$ CGO_ENABLED=0 go build ./cmd/helix
# github.com/agenthands/helix/internal/semantic/extract
internal/semantic/extract/provider.go:31:36: undefined: tree_sitter.Language
EXIT=1
```

**Root cause:** `internal/semantic/extract/provider.go` has NO build tag and unconditionally imports `tree_sitter "github.com/tree-sitter/go-tree-sitter"`. The upstream `tree-sitter/go-tree-sitter@v0.25.0/language.go` is a `#cgo`-using file, so under CGO=0 the upstream package fails to compile and `tree_sitter.Language` (used at `provider.go:31`) is undefined. Daemon imports this package unconditionally (`daemon.go:39`), so the failure propagates to `cmd/helix`.

**Why P57 was not affected:** P57 ships `extract_cgo.go` / `extract_nocgo.go` and per-language `provider_nocgo.go` stubs (verified at `internal/semantic/extract/golang/provider_nocgo.go`, etc.) — but the **shared `provider.go` interface file lacks the same split** and pulls in the cgo-only upstream type at the interface level.

**Impact on Phase 58 release pipeline:** `.goreleaser.yaml:13-14` pins `CGO_ENABLED=0` for the entire build matrix (darwin/linux/windows × amd64/arm64). The next `goreleaser build` will fail at every target. The cosign keyless signing path (REL-01), upgrade verifier (REL-05), and forwarder span unification (REL-06) cannot ship a release artifact until this is fixed.

**Fix sketch:** split `provider.go` into a CGO-tagged file (keeps `TreeSitterLanguage() *tree_sitter.Language`) and a no-CGO sibling that uses `any`/an interface, OR add `//go:build cgo` to `provider.go` and provide a no-CGO interface stub. The pattern is already established in `extract_cgo.go` / `extract_nocgo.go`.

## WARNING 1 — Lazy-init activation does not kick `ScheduleInitialExtraction`

**Affects:** EXTRACT-01 (extraction scheduling under default lazy-activation flow).

**Symptom:** `lazyActivateFn` at `daemon.go:438-455` (used by `LazyInitMiddleware` on first MCP tool call) activates the kernel workspace and updates session/repomap state but does NOT call `semanticScheduler.ScheduleInitialExtraction`. Only the explicit `activate_project` callback at `daemon.go:462-495` does.

**Why this is WARNING not BLOCKER:** the scheduler's `RequireReady` gate auto-kicks on cold workspaces (`ready.go:109` with `Reason: "require_ready_cold"`), so the first consumer of semantic data will trigger extraction. But (a) consumers paying attention to start-time will see a cold-start delay they would not see if they explicitly called `activate_project`; (b) any future tool that reads the store without going through `RequireReady` would see an empty store on a lazy-activated workspace.

**Fix sketch:** mirror the `if semanticScheduler != nil { ScheduleInitialExtraction(...) }` block from line 481-489 inside `lazyActivateFn`.
