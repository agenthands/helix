## Findings

### F-01 (HIGH) — Phase 62 ApplyRepair short-circuits on every production live edit

**From:** `internal/semantic/live/handler/handler.go:376-421` (`updateChangedFileWithKind`)
**To:** `internal/daemon/rank_wiring.go:101-110` (`rankBundle.engine`) → `internal/semantic/graph.Engine.ApplyRepair`
**Affected REQ-IDs:** GRAPH-01, GRAPH-02, LIVE-04 (live → graph delta application), and indirectly every Phase 64+ MCP tool that reads `semantic_graph_scores`

**Evidence:**
- `handler.go:376` constructs `recorder := &FileFactDiffRecorder{}` per tx span.
- `handler.go:377` checks `h.populateRecorderForTest != nil` — but the only writer of that field is `SetPopulateRecorderForTest` in `internal/semantic/live/handler/export_test.go` (test-only `_test.go` file).
- `handler.go:393-406` then takes the empty-diff branch on every production call: `recorder.IsEmpty() == true` → emits the once-INFO log per `(repoID, Handler instance)` via `emptyDiffOnce` and SKIPS `ApplyRepair`.
- Production grep for `RecordSymbol{Added,Removed,Changed}` and `RecordEdge{Added,Removed}` returns ZERO hits outside `_test.go` files. The recorder methods exist but nothing calls them in the live tx path.

**Severity rationale (HIGH not BLOCKER):**
The 62-09 closure that landed 2026-05-07 added the seam, the recorder, and the once-INFO log specifically to make this gap *visible*. The system therefore behaves as documented: ApplyRepair short-circuits, scheduler.Notify is never called from the post-commit path, `semantic_graph_scores` rows for live-edited files stay at the version they were on extraction. This is not a regression of any past behaviour. But it does mean Phase 62's "live edits advance graph_version" headline is FALSE for production today — it is true only under tests that install `SetPopulateRecorderForTest`. Operators monitoring the once-INFO log will see one entry per workspace; nothing else surfaces this gap until Phase 60 P04 lands.

**Recommended action:**
1. ROADMAP.md already tracks this as a Phase 60 P04 dependency. Confirm it stays on the v1.11 critical path.
2. Add a smoke assertion to the v1.10 release-smoke (or a daemon E2E test) that drives a `replace_symbol_body` against a fixture, then asserts the once-INFO log fired and `current_graph_version` did NOT advance — i.e. assert the *known-degraded* state explicitly so a future fix doesn't silently regress observability.
3. Surface the once-INFO log into a counter (e.g. `helix_semantic_live_apply_repair_skipped_total{reason="empty_diff"}`) so operators see a non-zero rate proportional to live edits, parallel to the `stub_no_data` harness in F-02. Today the only signal is a single INFO log per workspace per process, which can be missed in `LOG_LEVEL=warn`.

### F-02 (MEDIUM) — `rankStoreAdapter` 4 read methods are Phase-64-deferred stubs

**From:** `internal/daemon/rank_wiring.go:284-356`
**To:** `internal/semantic/store` typed effective-graph queries (Phase 64)
**Affected REQ-IDs:** GRAPH-03, GRAPH-05 (effective-graph reads), all PageRank scheduling against real data

**Evidence:**
- `QueryEffectiveGraph`, `QueryEffectiveAdjacency`, `CountStaleScoreRows`, `MarkAllScoreRowsStale` all return empty/zero values (`rank_wiring.go:331-357`).
- 62-08 closure added `stubObserve.emit(repoID, method)` to each → fires `SemanticGraphRepairInc("stub_no_data")` AND a once-WARN log. The `"stub_no_data"` label is a real registered enum value (`internal/obs/metrics.go:720`) and the family is scanned by the metrics-labels test (`metrics_labels_test.go:191`).
- These observability hooks fire ONLY when something actually calls the stub methods — i.e. when a per-workspace `RankScheduler` fires its incremental path after a `GraphVersionAdvance` event. Per F-01 above, `GraphVersionAdvance` is never emitted in production today, so the stub-no-data counter will also stay at zero in production.

**Severity rationale (MEDIUM not HIGH):**
This is the documented Phase-64 follow-up surface. The four stubs return zero-value, error-free responses so the scheduler does not crash. The only damage is that PageRank scores against the real effective graph are never computed; rank-aware MCP tools (Phase 64 surface) will see empty score rows. This was always a Phase 64 deliverable.

**Recommended action:**
1. Document explicitly in `v1.10-MILESTONE-AUDIT.md`'s "Known limitations shipped to v1.10" section.
2. The combination of F-01 + F-02 means BOTH halves of the rank pipeline are runtime-disconnected; neither half exercises the other. Treat F-01 closure (any populator) as the precondition for F-02 closure being verifiable.

### F-03 (MEDIUM) — Three vet analyzers are NOT in CI

**From:** `cmd/vet-noduckdb`, `cmd/vet-nokernel2semantic`, `cmd/vet-nosemantic2kernel`
**To:** the kernel⊥semantic and noduckdb-leak boundaries (foundational across Phases 57, 60, 61)
**Affected REQ-IDs:** STORE-06 (CGO=0 stub principle, now reframed as DuckDB import boundary), ENRICH-01 (kernel⊥semantic invariant), the entire Phase 57→60→61 layering invariant

**Evidence:**
- `Makefile:28-32` `vet:` target runs all three analyzers locally.
- `.github/workflows/go-test.yml:93-94` runs ONLY `go vet ./...` — none of the three custom singlecheckers are invoked. Searched all `.github/workflows/*.yml` for `vet-noduckdb`, `vet-nokernel2semantic`, `vet-nosemantic2kernel`: zero matches.
- Today the analyzers are local-only enforcement. A drive-by import that violates any of the three boundaries will pass CI green and only break the next developer who runs `make vet`.

**Recommended action:**
Add a CI step to `go-test.yml` that does the equivalent of `make vet` (install the three vettool binaries via `go install`, then run each `go vet -vettool=<bin> ./...`). The work is mechanical and the analyzers already pass — this is purely closing the CI loop.

### F-05 (LOW) — Lazy-init activation still skips `ScheduleInitialExtraction`

**From:** `internal/daemon/daemon.go:565-582` (`lazyActivateFn`)
**To:** `internal/semantic/scheduler.Scheduler.ScheduleInitialExtraction`
**Affected REQ-IDs:** EXTRACT-01

**Evidence:**
Carry-over from the 2026-05-04 audit. The explicit `activate_project` MCP callback at `daemon.go:608-616` correctly calls `semanticScheduler.ScheduleInitialExtraction`; the lazy-init middleware path at `daemon.go:565-582` does not. Mitigated by `RequireReady`'s cold-start kick (`internal/semantic/scheduler/ready.go:109` per the 2026-05-04 cite).

**Severity rationale (LOW, downgraded from WARNING):**
Production traffic that uses lazy-init (i.e. clients that send a tool call before `activate_project`) trigger extraction via `RequireReady` on first read of semantic data. The cold-start delay is observable but not data-corrupting.

**Recommended action:**
Three-line fix mirroring the explicit-activation block. Defer to next phase that touches `daemon.go` activation wiring.

### F-06 (LOW) — `helix upgrade` daemon-detect short-circuit not exercised in CI smoke

**From:** `internal/upgrade/daemon_detect.go` (RunningInDaemon)
**To:** `helix upgrade` cobra entrypoint
**Affected REQ-IDs:** REL-05

**Evidence:**
The `HELIX_RUNNING_AS_DAEMON=1` env var is set at `daemon.go:737`; `internal/upgrade/daemon_detect.go` reads it. The release-smoke target in `Makefile:77-157` boots the daemon and hits MCP `tools/list`, but does NOT shell into the running daemon's process tree to invoke `helix upgrade` and verify the short-circuit message. CONTEXT.md D-08 (T-52-04-08) documents this as a high-impact safety mechanism but there is no integration test for the seam.

**Recommended action:**
Add a smoke-test variant that runs `helix upgrade` from inside the daemon's exec'd shell to assert the short-circuit. Low priority — the failure mode is highly visible (daemon binary swap under itself) and the env-var contract is straightforward.
